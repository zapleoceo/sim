# Sim — архитектура MVP

Описание относится к коду, не к развёрнутой версии. Старые отчёты и ревью — в
[docs/history/](history/).

Платформа ИИ-персонажей: привлечение в Instagram, личное общение в WhatsApp и Telegram,
сопровождение клиента по воронке до регистрации и первой оплаты у партнёра.

Документированная схема: `https://sim.zapleo.com` → Cloudflare → nginx :80 → docker compose.
Репозиторная конфигурация LLM: только через AIbroker (`https://aib.zapleo.com`, проект `sim`, id 21, лимиты $0 — бесплатные
провайдеры + подписочные `claude-sub/*`, `codex-sub/*`).

## Принципы

1. **Слои и порты внешних систем.** `domain` содержит правила без IO; `ports` (Protocol)
   описывают каналы, LLM, синтез/распознавание речи и живой голос, `adapters` их реализуют; `api`/`worker` собирают зависимости
   (`sim/wiring.py`). В текущем коде `services` также напрямую используют SQLAlchemy,
   ORM-репозитории и инфраструктурные компоненты: строгой гексагональной изоляции пока нет.
   Новый канал добавляется через адаптер и реестр коннекторов (часть решений взята из stepan2).
2. **LLM — только Broker.** Ключей провайдеров в проекте нет. Модель задаётся на уровне персонажа
   (`persona.model`: пусто = цепочка Broker `chat:sales`, или точный pin `claude-sub/claude-sonnet-5-5`).
3. **Секреты каналов шифруются** (Fernet/MultiFernet, ключ из env, ротация через список ключей).
   Вход админов — только Telegram Login Widget (паролей нет). Сессии — httpOnly + Secure + SameSite=Lax cookie, CSRF-токен
   на мутирующих запросах.
4. **Персонаж следует редактируемому промпту.** Фиксированный блок идентичности больше не
   добавляется. Контролер не
   исправляет стиль и опечатки и не правит ответ по фактам из самого диалога; ему передаётся
   то же окно истории, что и персонажу (`GUARD_HISTORY_TURNS = HISTORY_LIMIT`).
5. **Оплаты и регистрации подтверждает только партнёр** (webhook с HMAC или импорт CSV),
   не ИИ и не оператор вручную по словам клиента.
6. **Без Redis.** Очередь задач — таблица `job` в Postgres (`FOR UPDATE SKIP LOCKED`). Исходное обоснование в репозитории —
   ограниченная RAM сервера; текущий объём свободной памяти не измерялся.

  domain/              enums, воронка (переходы этапов), чистые правила; без IO
  clock.py             Clock (источник времени, naive UTC) и utcnow()
  ports/               Protocol-интерфейсы: ChannelPort (и PollingChannelPort), LLMPort, SpeechPort, LiveVoicePort
  adapters/
    crypto.py          Fernet (из stepan2)
    llm/broker.py      клиент Broker: POST /v1/jobs → poll GET /v1/jobs/{id} (из stepan2, упрощён)
    channels/          telegram.py (Bot API), whatsapp.py (Evolution API), instagram.py (instagrapi)
    db/                ORM-модели, репозитории
  connectors/          ConnectorSpec + REGISTRY (kind → как собрать порт, capabilities)
  services/

    ingest.py          входящее сообщение → клиент/диалог/сообщение, дедуп по external_id
    conversation.py    сборка промпта (персона + стратегия + этап + история) → Broker → JSON-решение
    outbound.py        отправка через канал (сразу после генерации), ручной режим оператора

    followup.py        повторный контакт при отсутствии ответа (по сценарию)

    unanswered.py      сообщения клиента без ответа; предупреждение о долгом ожидании
    reply_journal.py   журнал несозданных ответов (шаги watch журнала системы)

  api/                 FastAPI-роутеры (/api/...), webhooks (/hooks/...)

## Воронка

Этапы (по порядку): `first_contact` → `engaged` → `needs_identified` → `interested` →
`handed_to_partner` → `registered` → `paid`.

Статусы поверх этапа: `active`, `paused` (оператор/клиент попросил паузу), `no_response`
(лестница фоллоу-апов исчерпана), `refused` (отказ). Возврат к диалогу: новое входящее
сообщение переводит `no_response`/`paused` обратно в `active`, этап не теряется.

ИИ может продвигать этап только до `handed_to_partner` включительно и только вперёд.
`registered` и `paid` ставит исключительно `partner.py` по данным партнёра.

## Поток сообщения

```
канал ──webhook/poll──▶ ingest ──▶ message(in) + job(reply, run_at=now+debounce)
                                   └▶ job(media) для вложения (webhook сети не трогает)
worker ──▶ job(media): channel port.download_media(ref) → файл; голос → Broker transcribe → text
worker ──▶ job(reply): ai_paused? → стоп с записью в журнале (см. «Пауза ИИ и сообщения без ответа»);
                     открытый media-job диалога → ждать (повтор через 3 с)
                     один reply на диалог (advisory lock); промпт → Broker → {reply, stage, ...}
                     пришло новое сообщение клиента за время вызова → ответ отбрасывается,
                     следующий job отвечает с полным контекстом
                     контролер (guard) проверяет черновик → ok / rewrite / block (см. ниже)
                     funnel.advance(...) ; outbound.queue_ai(текст после контролера, delay) → job(send)
оператор в админке ──▶ outbound.send(manual): ИИ на паузе, неотправленные ответы ИИ отменяются
```

История реального диалога включает входящие и только `sent` исходящие сообщения.
Фильтрация происходит до лимита истории; `queued`, `failed`, `cancelled` и guard-blocked
черновики не воспринимаются как увиденные клиентом. Inbox сохраняет все записи.
Аналитический `replied` также учитывает только `sent` исходящие без
`guard_verdict=blocked`, сохраняя все входящие. Период и порядок определяются
по `created_at`, отдельного `sent_at` нет; это приближение хронологии доставки. Счётчики
`guard` включают сохранённые вердикты неотправленных сообщений.

Правки сообщений Telegram (`edited_message`) сохраняются с пометкой «[изменено]», но нового
ответа ИИ не вызывают. Правка approved/scheduled поста оператором (не owner) возвращает его в `draft`.

Ответ модели — JSON (`response_format: json_object`). Если JSON не разобрался — один повтор, затем
диалог помечается для оператора, клиенту ничего не уходит.

## Пауза ИИ и сообщения без ответа

Пауза ИИ диалога (`dialog.ai_paused`) полностью останавливает ответы персонажа: задача `reply` не
создаётся и ничего не генерирует. Паузу ставят: ответ оператора из админки, сообщение с телефона
аккаунта, передача оператору (решение модели, отказ контролёра, исчерпанные попытки `reply`) и
переключатель «ИИ» в диалоге. Снимает её только `AiPauseService.resume`
(`sim/services/ai_pause.py`, `POST /api/dialogs/{id}/ai`); новый способ снять паузу обязан идти
через него.

**Сообщение без ответа** (`sim/services/unanswered.py`, одно определение для карточки диалога,
восстановления и надзора): сообщение клиента после последнего исходящего сообщения диалога,
которое не отменено. Отменённый ответ ИИ (`cancelled`) до клиента не дошёл и ответом не считается;
`queued`, `sent` и `failed` считаются. Правка сообщения клиентом («[изменено]») новой репликой не
является. По тому же правилу задача `reply` решает, есть ли на что отвечать
(`MessageRepo.last_effective`).

**Журнал.** Пропуск ответа не бывает молчаливым. `ReplyJournal` (`sim/services/reply_journal.py`)
пишет шаг журнала системы с типом `watch` («Контроль ответов») и строку в лог процесса, с id диалога
и id сообщения:

| Запись (`name`) | Статус | Когда | `detail` |
|---|---|---|---|
| «ответ не создан: диалог на паузе ИИ» | `skipped` | входящее сообщение сохранено в диалоге на паузе (`source: inbound`) или задача `reply` дошла до диалога на паузе, где клиент ждёт ответа (`source: reply_job`; у шага задачи `reason: ai_paused`) | `reason`, `source` |
| «ответ поставлен после снятия паузы ИИ» | `ok` | пауза снята, поставлена одна задача `reply` | `unanswered` — сколько сообщений ждало |
| «пропущено, устарело» | `skipped` | пауза снята, но сообщение старше окна; по записи на каждое сообщение | `age_min`, `window_min` |
| «входящее без ответа дольше порога» | `warning` | ИИ включён, а сообщение клиента ждёт дольше порога | `waiting_s`, `threshold_s`, `unanswered` |

**Восстановление после паузы.** `resume` снимает паузу и `needs_operator`, затем берёт сообщения
без ответа:

- их нет — ничего не делает (`recovery.status = none`);
- последнее из них не старше окна — ставит одну обычную задачу `reply` на диалог
  (`IngestService.queue_reply`: тот же ключ `reply:<dialog>`, та же пауза `reply_debounce_s`).
  Персонаж отвечает один раз, на последнее сообщение, видя в истории все (`queued`);
- последнее старше окна — автоматического ответа нет, ожидающая задача `reply` диалога отменяется,
  в журнале «пропущено, устарело» (`stale`); отвечает оператор;
- клиент в статусе `refused` — задача не ставится (`refused`).

Окно — настройка владельца `pause_recovery_window_min` («Окно ответа после паузы ИИ, мин», группа
«Ответы», по умолчанию 120, от 1 до 10080). Возраст считается по времени сообщения в канале
(`message.created_at`).

**Надзор за ответами.** Worker раз в `SIM_UNANSWERED_WATCH_INTERVAL_S` (60 с) вызывает
`UnansweredService.warn_overdue`: в диалогах, где ИИ включён и клиент не отказался, самое старое
сообщение без ответа, которое ждёт дольше `SIM_UNANSWERED_WARN_S` (300 с) и пришло не раньше чем
сутки назад, получает одно предупреждение в журнале. Повторно то же сообщение не записывается
(проверка по `trace_event`). Наружу ничего не отправляется: запись предназначена для будущего
оповещения.

## Контролер, он же Охранник (pre-send guard)

Каждое сообщение, написанное ИИ (ответы **и** фоллоу-апы; сообщения оператора не проверяются),
проходит второй вызов LLM до постановки в очередь отправки. Генератор работает на
`persona.model` или `chat:sales`; контролер — на **другой ротации Broker**: capability из
`SIM_GUARD_CAPABILITY` (по умолчанию `structured`, groq-first, надёжный JSON), `json_mode`.
Если вернувшаяся модель (`LLMResult.model`) совпала с моделью генератора, контролер один раз
перезапускается на `SIM_GUARD_FALLBACK_CAPABILITY` (по умолчанию `prefilter`); оба вызова
видны в `llm_call` (`workflow = "guard"`, поля `capability`/`model`).

После fallback известное повторное совпадение ID с исходным генератором вызывает
`GuardError`: сообщение не ставится на отправку. Сравнение игнорирует регистр и пробелы
по краям, включая проверку rewrite. Отсутствующие ID пока допускаются, разные ID могут
быть алиасами. Rewrite сравнивается с исходным генератором, поэтому контролер может
проверять собственную правку. Полная независимость модели этим не доказана.

Охранник это отдельная роль с одним промптом (страница админки «Агенты», карточка «Охранник»: «Модель» `guard_model` и
«Промпт охранника» `guard_prompt`; маршруты `guard_capability`, `guard_fallback_capability` в
`app_setting` меняются только через API). Персона и стратегия охраннику не передаются: у персонажей
широкая свобода, остальные ограничения настраиваются в симуляторе.

Вход: system = промпт охранника (`guard_prompt`, один редактируемый текст: роль, вход, правила,
вердикты и JSON-формат; по умолчанию правила: не просить пароли, коды и карты; без ссылок, кроме
разрешённых; без обещаний гарантированного дохода; уважать «не пишите»; всё остальное не
нарушение) + контракт согласованности управляющих полей `GUARD_CONTROL`. user = JSON: последние `history_limit`
реплик диалога (текст клиента только здесь), черновик, этап, `allowed_links` (ссылка регистрации
клиента и ссылки на другие каналы персоны). Выход: `{"verdict": "ok"|"rewrite"|"block",
"violations": [...], "fixed_reply": "..."}`.

Персонаж свой ответ по замечаниям охранника не переписывает: при `rewrite` правку пишет сам охранник.

* `ok` → уходит черновик. `rewrite` → берётся `fixed_reply`, который проверяется контролером ещё
  раз; не `ok` → `block`. `block` → ничего не отправляется, `dialog.needs_operator = true`,
  сообщение хранится как `cancelled` с `guard_verdict = blocked`, нарушениями (`error`,
  `guard_violations`) и текстом черновика; в промпт следующих ответов оно не попадает.
* Закрыто на отказ: ошибка/таймаут контролера или неразобранный JSON → `LLMError`, reply-job
  повторяется (штатные retry/backoff), после последней попытки диалог получает
  `needs_operator`. То же для job фоллоу-апа. Неохраняемых сообщений не бывает.
* В `message`: `guard_verdict` (`ok`/`rewritten`/`blocked`), `guard_violations`, `guard_model`
  (модель, давшая итоговый вердикт), `original_text` (черновик, если исправлен).
* Системный промпт охранника определяется только `guard_prompt` и контрактом `GUARD_CONTROL` (без персонажа, дат, id и данных
  клиента) и поэтому байт-в-байт стабилен для кеша провайдера.

## «Прочитано», «печатает…» и «записывает голосовое…»

Когда персона берётся за ответ клиенту (`run_reply`, не напоминание), она сначала отмечает его сообщения
прочитанными до последнего входящего (`services/chat_activity.py`, `mark_read`): клиент видит «прочитано».
Затем, пока модель пишет ответ и его проверяет охранник, в чате висит статус по тому, как уйдёт ответ: «записывает
голосовое…», если ответ будет голосовым (то же правило `will_speak` / `domain.voice.speaks`, что решает голос),
иначе «печатает…». Пока синтезируется голосовое (`OutboundService.voice_note`), тоже «записывает голосовое…».
Когда ответ разбит на несколько сообщений (`humanize.bubbles`, до 3 частей по пустой строке в ответе модели),
первая часть уходит сразу, а перед каждой следующей персона «набирает» её: задача `send` этой части несёт в
payload `typing_s` и в `OutboundService.typed` держит паузу с показанным «печатает…» на всё её время, затем
снимает статус и отправляет. Длина паузы — `humanize.typing_pause_s`: длина части / `TYPING_CHARS_PER_S`
(28 символов в секунду), не меньше `TYPING_MIN_S` (1 с) и не больше `TYPING_MAX_S` (6 с). Задача следующей
части стартует (`run_at`) в момент, когда должна уйти предыдущая. После паузы сообщение и диалог перечитываются:
если за это время оператор перехватил диалог, ИИ поставили на паузу или клиент отказался, часть отменяется.
Одиночное сообщение уходит без паузы и без статуса на отправке; голосовой ответ всегда одно сообщение, пауз
между частями у него нет.
Статус живёт в мессенджере несколько секунд, поэтому `showing` повторяет его каждые ~4 с до конца работы, но
не дольше `MAX_SHOW_S` (60 с): зависший шаг (медленная модель, задание Broker в очереди) не оставляет «печатает…»
висеть. По окончании работы статус сразу снимается действием `cancel`: Telegram-аккаунт — `SendMessageCancelAction`,
WhatsApp — presence `paused`; у Telegram-бота отмены нет, статус гаснет сам за ~5 с.
Каналы с `Capability.CHAT_ACTION`: Telegram-бот (`sendChatAction` typing / record_voice), Telegram-аккаунт
(`messages.setTyping`), WhatsApp (Evolution `chat/sendPresence` composing / recording). Instagram без статуса.
Каналы с `Capability.MARK_READ`: Telegram-аккаунт (`messages.readHistory` до id сообщения) и WhatsApp (Evolution
`chat/markMessageAsRead`); Telegram-бот прочитанное не отмечает (это делает сам Telegram). Ошибка статуса или
отметки никогда не мешает ответу.

## Звонки (Telegram-аккаунт, Gemini Live)

Персонаж с `accept_calls` берёт трубку, когда ему звонит клиент, с которым уже есть переписка, и
говорит голосом в реальном времени через Broker `/v1/live` (Google Gemini Live). Порт
`ports/live_voice.py` (`LiveVoicePort`), адаптер `adapters/llm/broker_live.py`, мост py-tgcalls
`adapters/channels/tg_calls.py` на том же Telethon-клиенте воркера (`Capability.ACCEPT_CALL`,
`TelegramUserConnector.listen_calls`, `Worker.answer_call`), сервис `services/calls.py`, промпт
`services/call_prompt.py`. Расшифровка звонка после разговора попадает в диалог. Подробно:
[calls.md](calls.md).

## Команда `/reset` (тестирование с чистого листа)

Сообщение `/reset` в любом чате канала (от клиента или набранное на самом подключённом аккаунте; регистр и
суффикс `@бот` не важны) не сохраняется и не получает ответа: `services/dialog_reset.py` стирает все сообщения
диалога, отменяет ожидающие ответ и напоминание, обнуляет счётчики диалога и контекст клиента (этап
`first_contact`, статус `active`, потребности, заметки, следующий шаг, паспорт лида) и отменяет его обновление. Клиент, его ref-код и связи с каналами,
события воронки и партнёра и журнал запросов остаются; в самом мессенджере ничего не удаляется. Следующее
сообщение начинает новый разговор. Шаг в журнале: `inbound` с `detail.reset = true`.

## Паспорт лида и паспортистка

У каждого лида есть паспорт: один текст (`client.passport`, до 12 000 символов) о человеке (кто он, жизнь,
работа, семья, цели и боли, отношение к предложению, как общается) и о том, что персонаж уже рассказал ему о
себе, чтобы не противоречить. Ведёт его отдельный агент «паспортистка» (`services/passport.py`): после каждого
ответа персонажа `ConversationService.apply` ставит задачу `passport` (одна на диалог, `passport_key`,
повторные ответы склеиваются, задержка 5 с). Паспортистка получает system = свою инструкцию
(`passport_prompt`) и user = JSON `{persona, passport, dialog}` (слова клиента только как данные), модель
`passport_model` (пусто: маршрут `chat:sales`), workflow `passport` в аудите; возвращает весь обновлённый
паспорт. Пустой ответ старый паспорт не стирает. Персонаж читает паспорт в динамическом контексте каждого
ответа блоком «ПАСПОРТ СОБЕСЕДНИКА», помеченным как данные, а не инструкции. Паспорт виден в карточке
клиента (только чтение), `/reset` его очищает. Инструкция и модель паспортистки правятся на странице
«Агенты» рядом с охранником.

## Живое обновление админки (без опроса)

Страница «Диалоги» обновляется в момент изменения, а не по таймеру. Любая транзакция, которая добавляет, меняет или
удаляет `message` либо меняет `dialog` (приём в воркере, ответ персоны, квитанция отправки, действие оператора,
`/reset`), при коммите шлёт `pg_notify('sim_live', {"dialogs": [id…]})` (хуки сессии SQLAlchemy,
`services/live.py`, ставятся в `build_container`). API-процесс слушает канал и раздаёт id всем открытым потокам
`GET /api/events` (Server-Sent Events, только вошедшие админы). Админка (`lib/live.ts`) по событию перезапрашивает
список диалогов и изменившиеся диалоги. В событиях только номера диалогов, без текста: страница перечитывает данные
обычным API со своими правами. Пульс каждые 15 с держит соединение через nginx и Cloudflare (`X-Accel-Buffering: no`),
браузер сам переподключается через 3 с; опрос раз в 30 с остаётся запасным. Откатанная транзакция ничего не шлёт.

## Лид принадлежит персоне

`client.persona_id` задаётся при первом контакте и никогда не меняется. Один человек в разных
каналах **одной** персоны — один клиент: при первом сообщении новой identity ingest ищет
клиента этой же персоны (1) по ref-коду в тексте (`#<код>` или `/start <код>`; код вырезается из
текста, который видит ИИ) и (2) по совпадающему телефону. Найден → identity добавляется к
существующему клиенту, для нового канала создаётся новый `dialog` (история видна в карточке
клиента). Между персонами слияния нет; на канале, где у клиента уже есть identity, слияние не
делается (это другой человек).

Чтобы перевести клиента в другой канал, в динамический блок промпта попадают ссылки на другие
активные каналы персоны, уже с ref-кодом: WhatsApp `https://wa.me/<номер>?text=<приветствие #код>`,
Telegram-бот `https://t.me/<бот>?start=<код>`, Telegram-аккаунт `https://t.me/<username>?text=<…>`.
Эти же ссылки разрешены контролеру.

## Prompt caching

Порядок сообщений, отправляемых в Broker: `system` = неизменный текст персоны + стратегии
(одинаков байт в байт для всех клиентов персонажа: без дат, имён, id), затем история диалога,
затем `system`-блок с динамикой (этап, заметки, текущее время, ссылки на другие каналы).
Стабильный `system` = промпт персонажа (`description`),
стратегия (оффер, `prompt`, подсказки по этапам, мягкие правила) и формат ответа `output_contract`; посмотреть его целиком можно на странице персонажа (`GET /api/personas/{id}/prompt`). Брокер сам ставит брейкпоинты
для Anthropic; эффект проверяется по `cache_read_input_tokens` в `llm_call`.

## Симуляции в боте входа

Админ (любая роль, активный `admin_user` по `telegram_id`) пишет боту входа (`@stepanv2bot`,
`SIM_TG_LOGIN_BOT_TOKEN`) как клиент и получает ответ персонажа. Telegram Login Widget от webhook
не зависит. Остальным бот отвечает одной строкой отказа и ничего не раскрывает.

```
Telegram ──POST /hooks/admin-bot (секрет в заголовке)──▶ AdminBot.handle
   команды и кнопки: меняют sim_branch и отвечают сразу
   текст/голос: sim_message(client) + job(sim_reply) — вебхук возвращает 200 сразу
worker ──▶ job(sim_reply): try_lock(NS_SIM, branch) → «печатает…» (sendChatAction каждые 4 с)
          → [голос: getFile → Broker transcribe] → SimulationService.reply → sendMessage
```

* Команды: `/start`, `/persona` (кнопки активных персонажей, новая ветка), `/new`, `/branches`
  (последние 10, кнопки «продолжить»), `/stage`, `/end`, `/debug on|off`. Подпись под ответом
  (курсивом): `этап · модель · guard: ok|исправлено|заблокировано`. Блок контролера показывает
  черновик и нарушения всегда.
* **Один движок, не копия.** `ConversationService.draft_reply` (сборка промпта + вызов Broker +
  разбор решения + контролер) общий для превью и симуляций; история — `visible_turns` (черновик,
  заблокированный контролером, в историю не входит); этапы — `domain.funnel.advance_by_ai`
  (те же правила, что у настоящего клиента: вперёд, не дальше `handed_to_partner`). Отличие одно:
  состояние лежит в `sim_branch`, а не в `client`. Контекст: имя «Тест <имя в Telegram>», ref-код
  `SIM<id ветки>`, канал `telegram`.
* Отказ клиента (`refused`/`stop_contact`) и передача оператору останавливают ответы в ветке,
  как в настоящем диалоге; `/new` начинает заново.
* Одно решение в работе на ветку: пока есть открытый `sim_reply`, новое сообщение получает
  «ещё готовится» и не сохраняется; в job — `NS_SIM`-замок. Две попытки job, потом админу уходит
  сообщение об ошибке.
* Вебхук: секрет = `hmac_sha256(SIM_SECRET_KEY, "admin-bot:" + токен)`, без новых переменных
  окружения. API при старте в `prod` вызывает `setWebhook` (идемпотентно; ошибка логируется без
  токена и API не останавливает); вручную — `python -m sim.cli admin-bot-webhook`.
* Админка: страница «Симуляции» (owner+, только чтение): список веток и переписка с бейджами
  контролера и моделью каждого сообщения. Симуляции не создают `client`/`dialog`/`message`,
  не видны в инбоксе и аналитике, ничего не отправляют в реальные каналы.

`sim.seed` заполняет только пустое. `python -m sim.cli apply-persona-prompts` ПЕРЕЗАПИСЫВАЕТ

## Каналы

| Канал | Транспорт | Как подключается | Приём | Риски |
|---|---|---|---|---|
| Telegram (бот) | Bot API (официально) | токен бота от @BotFather | webhook `/hooks/telegram/{channel_id}` + `secret_token` | нет |
| Telegram (аккаунт, `telegram_user`) | Telethon (MTProto, личный аккаунт, userbot) | `api_id`/`api_hash` с my.telegram.org → API development tools; вход по QR-коду (по умолчанию) или по телефону и коду; пароль 2FA | по событию: клиент воркера слушает новые входящие в личке (Telethon `NewMessage`) и сразу запускает опрос канала; запасной опрос раз в ~90 с (`SIM_TG_USER_POLL_INTERVAL_S`) | ограничение/бан аккаунта при подозрительной активности; FloodWait |
| WhatsApp | Evolution API v2 (Baileys, self-hosted) | QR-код в админке | webhook Evolution → `/hooks/evolution/{channel_id}` (внутренняя сеть, apikey) | неофициальный клиент, риск бана номера |
| Instagram | instagrapi (private API) | логин/пароль (+2FA/challenge код) в админке | опрос раз в ~2 мин в worker | риск checkpoint/бана; прокси с geo как у логина |

Данные подключения любого канала (токен бота, api_id / api_hash / телефон, логин, прокси) сохраняются
зашифрованно в `channel.session_enc` под `saved_credentials` (`ChannelService.connect`), поэтому повторное подключение
не требует ввода заново.

Telegram-аккаунт (`telegram_user`): StringSession (api_id, api_hash, string_session, прокси) хранится
зашифрованно в `channel.session_enc`; код входа и пароль 2FA нигде не сохраняются. Незавершённый
вход лежит в сессии под `pending` (с `phone_code_hash`), поэтому переживает рестарт. Куда Telegram отправил код
(`auth.sentCode.type`: приложение Telegram на других устройствах, SMS, звонок, почта, Fragment или
«сначала привяжите почту для входа») пишется в `pending.code_delivery`, в лог
(`telegram_user code sent … via <тип>`) и в подсказку админке (`CODE_WHERE`). Для сторонних API-приложений
код обычно приходит не по SMS, а в чат «Telegram» на других устройствах аккаунта.

Приём сообщений по событию: в воркере `TelegramUserConnector.listen()` включает у клиентов поток обновлений
(`receive_updates=True`), `TelethonTransport` подписан на `NewMessage(incoming=True)`, и новое сообщение в личном
чате ставит канал в `Worker.wake`: опрос этого вида каналов запускается на ближайшем тике (≤ `worker_tick_s`, 2 с),
а не через интервал. Сам опрос читает сообщение как обычно (курсор, дедупликация по `external_id`), поэтому
пропущенное событие (обрыв, деплой) лишь откладывает ответ до запасного опроса раз в ~90 с. В API-процессе клиенты
обновления не слушают.

Вход по QR-коду (`method: "qr"`, по умолчанию в админке): номер и код не нужны. `connect` вызывает Telethon
`qr_login()` и отдаёт `qr_data_uri` (SVG, `segno`) со статусом `pending`; админка опрашивает `state` раз в 3 с.
Владелец сканирует QR в Telegram на телефоне: Настройки → Устройства → Подключить устройство. Токен живёт ~30 с,
просроченный `state` заменяет новым (`qr.recreate()`). После скана: `active`, или `challenge` с `need: "2fa"`, если
на аккаунте облачный пароль (дальше обычный `verify`). Ожидание скана живёт в памяти API-процесса (`_qr`),
после рестарта `state` просит нажать «Подключить» ещё раз. Клиент
подключается без подписки на обновления (`receive_updates=False`) и ничего не помечает
прочитанным; читаются только личные диалоги с людьми (без групп, каналов, ботов и 777000).
Курсор по сообщениям (id на собеседника) живёт в памяти worker; после рестарта подхватываются
только непрочитанные и пришедшие за последние 24 ч (дубли отсекает `external_id`).
Отправка: чанки по 4096, минимум 3 с между отправками с аккаунта (`SIM_TG_USER_MIN_SEND_INTERVAL_S`),
FloodWait на отправке даёт `flood_wait:<секунды>` и повтор job по backoff. Отвязка делает `log_out`,
чтобы не оставлять «призрачное» устройство в сессиях аккаунта. Новое значение `ChannelKind` миграции
не требует: enum хранится как VARCHAR(32) без CHECK.

Голос: входящие голосовые → Broker `/v1/transcribe/jobs`. Исходящий голос персонажа — `SpeechPort`
(Broker `POST /v1/speech`, Google Gemini TTS) → ffmpeg OGG/Opus → `send_voice` канала; подробно в
[voice.md](voice.md). Видео (Vivix) не подключено. Кружочки ИИ — `VideoPort` (Broker `POST /v1/video/jobs`, Gemini Omni Flash) → ffmpeg квадрат 384 px со звуком → `send_video_note`, только на один аккаунт из настройки владельца, с кешем по хешу запроса: [video-notes.md](video-notes.md).

## Безопасность

- Webhook Telegram: проверка `X-Telegram-Bot-Api-Secret-Token` (секрет на канал).
- Webhook Evolution: доступен только из docker-сети, nginx не проксирует `/hooks/evolution`.
- Webhook партнёра: HMAC-SHA256 тела, секрет в env, защита от replay (timestamp ± 5 мин).
- Логин только через Telegram Login Widget: HMAC-SHA256 (секрет = sha256 токена бота), сравнение
  за постоянное время, `auth_date` не старше 1 часа и не из будущего (допуск 60 с), `hash`
  одноразовый (в БД, чистится по сроку); доступ только у активных админов из `admin_user`
  (приглашение по id или @username, `SIM_SUPERADMIN_TELEGRAM_IDS` — всегда superadmin).
  Break-glass: `python -m sim.cli login-link <id>` — одноразовая ссылка на 10 минут (sha256 в БД).
  Управление админами — только superadmin; последнего superadmin и себя убрать нельзя.
- Логин: rate limit по паре (telegram id, IP) и по IP (отдельного лимита на id нет — иначе чужой может
  заблокировать владельца). IP клиента берётся из `X-Real-IP`/`X-Forwarded-For` только если TCP-пир
  входит в `SIM_TRUSTED_PROXIES` (по умолчанию `127.0.0.1,::1,172.16.0.0/12`: nginx + docker-шлюз).
- В `SIM_ENV=prod` `/api/docs` и `/api/openapi.json` отключены.
- Все запросы к БД — через ORM/параметры; входящий текст клиента идёт в промпт только как
  user-сообщение, не в system (защита от prompt injection в персону).
- В логах нет секретов и полных текстов учётных данных.

## Решения «брать готовое / писать своё»

| Кандидат | Вердикт | Почему |
|---|---|---|
| stepan2 коннекторы (instagrapi, Evolution, Broker-клиент, crypto, ConnectorSpec) | брать | рабочий прод-код того же владельца, проверен на банах и таймаутах |
| Evolution API v2.3.7 | брать | уже используется в stepan2; Apache-2.0; self-hosted |
| instagrapi | брать | единственный живой вариант логина в IG без Meta App Review |
| Telegram Bot API напрямую через httpx | брать | 3 метода, отдельная библиотека не нужна |
| Telethon (userbot для `telegram_user`) | брать | MIT, живой (1.45.0), StringSession, `receive_updates=False`; прокси через python-socks |
| Pyrogram | нет | не поддерживается (заброшен); форки без гарантий |

## Очередь worker и доставка

`Worker.run()` держит до четырёх job: свободный слот заполняется без ожидания остальных,
проверки due job и polling продолжаются с `worker_tick_s`. Активные job этого worker
исключаются до лимита claim. При SIGTERM/SIGINT новые claim прекращаются, уже взятые
job/polling завершаются. `tick()` остаётся batch-вызовом для тестов/разовых запусков,
не для одновременной работы с `run()`. Истёкший lease позволяет другому worker повторно
взять долгую job. Порядок завершения не гарантируется.

Worker передаёт claim-time `attempts` как поколение и защищает complete/fail
условием `running` + то же поколение; claim повторно проверяет due/expired и attempts.
Terminal giveup выполняется только после применённого terminal-failure CAS. Lease renewal
и универсальный fencing побочных эффектов нет; старый владелец может завершить истёкший
lease, если нового claim нет. Старые worker нужно полностью вывести из работы перед запуском
новых. Подробный контракт и пределы: [API, очередь](api.md#fencing-состояния-очереди).

Для исходящих сообщений есть отдельный долговечный intent/receipt. При
неизвестном исходе повторный вызов транспорта блокируется и требуется оператор;
см. [границы доставки](outbound-delivery.md).

## Объединённая переписка и активность

`ActivityRepo` выполняет фильтрацию, count и ограниченную пагинацию в SQL с порядком
`created_at DESC, id DESC`. Контекст клиента/канала/персонажа загружается соединениями,
без отдельного запроса на каждое сообщение. Общие границы дат вынесены в `api/date_bounds.py`.
Роуты активности возвращают безопасные проекции, журнал LLM ограничен owner/superadmin.
Клиентская история объединяет диалоги по существующему `client_id`; разные персоны и
совпадающие имена не объединяются автоматически.

Миграция `0008` добавляет nullable `message.operator_id` и исторический `operator_name`,
а также индексы для страниц сообщений. Имя фиксируется при ручном ответе; старые записи
остаются неизвестными. Время отправки берётся только из receipt. Админка использует
общие компоненты содержимого/метаданных сообщения и ленты для карточки клиента и
журнала. [Руководство администратора](admin-activity.md).

## Журнал системы и трейсы

Цель: любой запрос можно отследить от начала до конца, с таймингами и попытками.

- **Контекст.** `sim/trace_context.py` хранит текущий трейс в ContextVar: id, кто действует и
  связи (клиент, диалог, канал, задача, сообщение).
- **Где рождается трейс:**
  - HTTP-мидлварь `sim/api/tracing.py` — для каждого `/api` и `/hooks`;
  - опрос канала — на каждое входящее сообщение;
  - worker — для задачи без трейса.
- **Продолжение в очереди.** `JobRepo.enqueue` сохраняет `job.trace_id`. Worker выполняет попытку
  внутри этого трейса, поэтому задачи `reply` → `send` попадают в тот же трейс.
- **Шаги пишет `Tracer`** (`sim/services/tracing.py`):
  - HTTP/webhook — метод, путь, код, длительность, админ;
  - `inbound` — `IngestService`;
  - `job` — попытка, ожидание в очереди, итог, повтор/ошибка, передача оператору;
  - `llm`/`guard` — `AuditedLLM` со ссылкой на `llm_call`;
  - `send` — транспорт в `OutboundService`;
  - `partner` — `PartnerService`;
  - `poll` — опрос с сообщениями или с ошибкой;
  - `watch` — `ReplyJournal`: ответ не создан из-за паузы ИИ, восстановление после паузы,
    устаревшее сообщение, входящее без ответа дольше порога (статус `warning`).
- **Когда шаги записываются.** Внутри scope шаги буферизуются и пишутся одной транзакцией после
  единицы работы. Поэтому они не конкурируют с открытой транзакцией запроса или задачи, и
  ошибочный шаг сохраняется, даже если работа откатилась. Запись журнала никогда не ломает
  саму работу.
- **Маскирование.** `mask()` убирает токены ботов, Bearer, `key=`/`token=`/`password=`,
  `user:pass@` и длинные непрозрачные строки. Тела, cookies и тексты сообщений не пишутся.
- **Чтение.** `TraceRepo` фильтрует и сортирует в SQL по любой колонке. Клиент шага берётся
  из `client_id` или через `dialog_id`.
- **Хранение.** Worker раз в `trace_purge_interval_s` удаляет шаги старше срока из настройки владельца
  `trace_retention_days` (по умолчанию env) пачками по 5000. HTTP-шаг берёт `client_id`/`dialog_id`/`channel_id` из параметров маршрута.
- **Админка.** Вкладка «Активность → Журнал» (по умолчанию у владельца):
  - таблица, где сортировка и фильтр в заголовке каждой колонки;
  - поиск, «Только ошибки», живой режим (обновление каждые 5 с) и пагинация;
  - боковая панель трейса: шкала шагов с длительностями, попытками, ошибками и расходом ИИ.

## Публикации и финансовые события

Один JPEG Instagram поддерживается только при `SIM_IG_CONTENT_ENABLED=true` и явном
`SIM_IG_CONTENT_POST_IDS`; значения по умолчанию false и пустой список. Нужны утверждённый
пост, активная персона и явно выбранный активный Instagram-канал этой персоны с сессией.
Удалённые URL, video/reel/story и несколько файлов не поддержаны. Полного upload/UI-пути нет.
До внешнего upload независимо коммитится постоянный intent; receipt сохраняется отдельно.
Неизвестный исход не разрешает повторный upload, редактирование или переутверждение.
Миграция 0006, консервативный fingerprint и границы восстановления описаны в
[publication-intents.md](publication-intents.md); условия отдельного включения — в
[instagram-content-publishing.md](instagram-content-publishing.md).
Наличие receipt не означает внешнюю проверку и не гарантирует exactly-once у Instagram.

CSV-строка без `external_id` и без явного `occurred_at` отклоняется без изменения воронки.
Только дата сохраняет прежний fallback-ключ с UTC timestamp; только ID использует время
первого импорта. Повтор ID (в пределах типа события) или fallback-ключа пропускается.
Разные платежи на одно время требуют разных ID; уже созданные дубли не удаляются.

Выручка и выплаты группируются по нормализованной валюте события, без FX-конвертации.
Неизвестная валюта — отдельная неподтверждённая группа. Старые скалярные суммы равны `null`
при нескольких валютах или группе без валюты; при отсутствии сумм — `0.0`. Выплаты включают
registration и payment, выручка — только payment. API и dashboard обновляются совместно.
Полный контракт: [api.md](api.md).
