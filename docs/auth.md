# Вход в дашборд

Код: `backend/sim/api/auth.py` (проверка, сессии, guard), `backend/sim/api/routes/auth.py`
(маршруты), `backend/sim/api/ratelimit.py` (ограничение попыток). Контракт — `docs/api.md`.

## Кто может войти

Только через Telegram Login Widget бота `SIM_TG_LOGIN_BOT_USERNAME` (в BotFather у бота
`/setdomain` = домен дашборда). Пускаем только **активную** строку `admin_user`
(`is_active = true`) с этим `telegram_id`. Остальным — `403 «Доступ не выдан»`.

Telegram ID из `SIM_SUPERADMIN_TELEGRAM_IDS` при первом входе получают строку `admin_user`
автоматически (и снова становятся активными, если их выключили). Ролей нет: все админы равны.

## Проверка виджета

`POST /api/auth/telegram` получает поля виджета (`id, first_name, last_name, username,
photo_url, auth_date, hash`) как есть.

1. Ключ — `sha256(SIM_TG_LOGIN_BOT_TOKEN)`.
2. Строка проверки — все непустые поля, кроме `hash`, отсортированные по имени,
   `key=value` через перевод строки.
3. `HMAC-SHA256(ключ, строка)` сравнивается с `hash` за постоянное время
   (`hmac.compare_digest`).
4. `auth_date` не старше часа и не больше чем на минуту в будущем (время — из `Clock`).

Нет токена бота → `503`. Подпись не сошлась или устарела → `401`.
Повторное использование того же `hash` в пределах часа не блокируется (защита от повтора
необязательна: подпись привязана к боту, а сессия всё равно серверная).

При успехе имя и username админа обновляются из профиля Telegram.

## Сессия

- Cookie `sim_session`: случайные 32 байта (`secrets.token_urlsafe`), `HttpOnly`,
  `SameSite=Lax`, `Path=/`, `Secure` — по `SIM_COOKIE_SECURE` (в проде `true`), срок —
  `SIM_SESSION_TTL_H` часов (по умолчанию 72).
- В базе (`auth_session`) хранится только `sha256` cookie, CSRF-токен и `expires_at`.
  Утечка базы не даёт войти. Просроченные строки удаляются при каждом новом входе.
- Сессия недействительна, если истёк срок или админа выключили (`is_active = false`).
- `POST /api/auth/logout` удаляет строку сессии и стирает cookie. Если сессия ещё жива,
  выход требует CSRF-токен (иначе чужой сайт мог бы разлогинить); с мёртвой cookie просто
  стирает её. Всегда `204`.

## CSRF

Ответы `POST /api/auth/telegram` и `GET /api/auth/me` содержат `csrf`. Фронт отправляет его
в заголовке `X-CSRF-Token` в каждом запросе, кроме `GET/HEAD/OPTIONS`. Нет или не совпал →
`403 «Неверный CSRF-токен»`. Токен один на сессию и хранится в `auth_session.csrf_token`.

## Guard

Весь роутер `/api` закрыт Litestar-guard `require_admin`: он находит сессию по cookie, кладёт
админа в запрос (зависимость `admin`) и проверяет CSRF. Открыты без входа только маршруты с
`opt={"public": True}`: `GET /api/auth/config`, `POST /api/auth/telegram`,
`POST /api/auth/logout` (проверяет сессию сам). Вне `/api` — `/healthz`, `/readyz` и статика
SPA. Файлы медиа (`/api/media/{id}/file`) и поток событий (`/api/events`) — только после
входа.

## Ограничение попыток

`LoginRateLimiter` в памяти процесса `api` считает **неудачные** входы (плохая подпись или
нет доступа) за скользящее окно 15 минут:

- пара «Telegram ID + IP» — не больше 5;
- один IP — не больше 20.

Сверх лимита — `429` с заголовком `Retry-After`. Удачный вход сбрасывает счётчики пары.
Ключа «только Telegram ID» нет намеренно: иначе кто угодно мог бы заблокировать владельцу
вход. IP берётся из TCP-соединения: за nginx это адрес прокси, поэтому лимит по IP общий на
всех (заголовки `X-Real-IP` не доверяем, пока нет настройки доверенных прокси).

## Ошибки

Все ответы об ошибке — `{"error": "текст"}`: `401` не вошёл / подпись не сошлась,
`403` нет доступа или CSRF, `429` слишком много попыток, `503` вход не настроен.
