# Каналы: Telegram, Instagram Direct, WhatsApp

Персонаж говорит через каналы — аккаунты мессенджеров. Telegram (личный аккаунт, Telethon)
описан в [telegram.md](telegram.md); здесь — общая схема и два новых канала: **Instagram Direct**
(приватное API через instagrapi) и **WhatsApp** (связанное устройство через Evolution API v2).

## Как устроено

Один канал = строка таблицы видов + свой адаптер. Больше ничего по виду канала не ветвится.

| Что | Где |
|---|---|
| Что умеет каждый мессенджер (подпись, что можно отправить, «печатает», «прочитано», звонки, как приходят сообщения, очередь задач) | `sim/domain/channels.py`, `SPECS` |
| Доставка исходящего (загрузить, «печатает», отправить, `mark_sent` / `mark_failed`, повторы) — одна для всех | `sim/channels/delivery.py` |
| В какую очередь идёт отправка, «прочитано», статус | `sim/tasks/queue.py` + `sim/channels/routing.py` |
| Вход из дашборда (одна форма на вид, дальше одинаково) | `sim/api/channel_logins.py`, `sim/api/routes/channels.py` |
| Учётные данные (Fernet JSON в `channel.credentials_enc`, как у Telegram) | `sim/channels/store.py` |
| Instagram: клиент, разбор, вход, отправка, опрос | `sim/channels/instagram/` |
| WhatsApp: HTTP Evolution, разбор, вход, отправка, вебхук | `sim/channels/whatsapp/` |
| Задачи очереди `channels` | `sim/channels/tasks.py` |

| | Telegram | Instagram Direct | WhatsApp |
|---|---|---|---|
| Вход | QR (+ пароль 2FA) | логин + пароль через прокси (+ код / подтверждение / проверка), или `sessionid`, или JSON сессии | QR (связанное устройство) |
| Приём | живая сессия (push) | опрос раз в ~2 мин | вебхук Evolution |
| Текст, фото | да | да | да |
| Видео, файл | да | нет | да |
| Голосовое | да | нет | да (PTT) |
| Кружок | да | нет | нет |
| «Печатает…» | да | нет | да (и «записывает аудио…») |
| «Прочитано» | да | «Просмотрено» | синие галочки |
| Звонки | да | нет | нет |
| Очередь задач / процесс | `telegram` / telegram | `channels` / worker | `channels` / worker |

Все входящие любого канала идут в один `Inbox.ingest` ([reply.md](reply.md)), поэтому
внимание, ход, проверка, память и паспорт работают одинаково. Новый собеседник — новый клиент с
выключенным ИИ, его идентичность — `client_identity` вида канала, адрес переписки —
`chat.external_thread_id` (id треда Instagram, jid WhatsApp; [database.md](database.md)).

### Что она может отправить в этом чате

`capabilities_of(persona, channel_kind)` (`sim/services/capabilities.py`) пересекает её
переключатели и модели с тем, что умеет мессенджер чата: в директе нет голосовых и видео, кружки
есть только в Telegram. Факты хода говорят модели «голосовые — нет; кружки — нет (в этом
мессенджере их нет)», проверка плана (`sim/services/plan_check.py`) отклоняет такое действие,
модель переписывает ответ. Звонки остаются только в Telegram.

### Как она пишет в этом мессенджере

К блоку «КАК ТЫ СЕЙЧАС ПИШЕШЬ» добавляются правила мессенджера
([writing.md](writing.md), «Каналы»): в директе коротко, с эмодзи, ответы на сторис,
незнакомые холоднее; в WhatsApp голосовые — норма, сообщения длиннее, он видит «печатает» и
галочки.

## Очередь `channels` и процесс

Отправка, «прочитано» и статус Instagram и WhatsApp — задачи очереди `channels`
(`channels:send_message`, `channels:mark_read`, `channels:chat_action`), их выполняет
**воркер** (третий воркер Procrastinate в `sim/apps/worker.py`, 3 параллельно). Отдельного
процесса нет: воркер и так всегда работает, его останавливает выкат перед миграциями, и
новых постоянных сервисов не появляется.

`ProcrastinateQueue` спрашивает у `DbChannelRouter`, какой мессенджер у чата (кэш: чат канал не
меняет), и ставит `f"{namespace}:send_message"` в очередь этого вида. Telegram — как раньше.
Мессенджер без «печатает» (Instagram) вообще не получает задачу статуса.

Без каналов Instagram и WhatsApp ничего нового не держит соединений: состояние очереди
`channels` (клиенты instagrapi, статусы) создаёт первая задача, которой оно нужно; к Evolution
ходят по HTTP на каждый запрос. Единственное, что крутится всегда, — `channels:instagram_tick`
раз в минуту: один запрос к таблице `channel`, и если Instagram-каналов нет — всё.

### Отправка без повторов

У Telegram повтор отбрасывается по `random_id` ([telegram.md](telegram.md)). У Instagram и
WhatsApp такого ключа нет, поэтому отправка **эксклюзивная** (`deliver(..., exclusive=True)`):

1. транзакция; `pg_try_advisory_xact_lock` по id сообщения — если его держит другая задача
   (то же сообщение уже отправляется), эта повторится позже;
2. сообщение уже не `pending` — пропуск;
3. «печатает», отправка и `mark_sent` — в той же транзакции.

Повторы: `RetryAfter` (мягкая блокировка Instagram, лимит отправок) — через запрошенные
секунды + 1; сеть / 5xx Evolution — 5, 10, 20, 40, 80 с; 4xx Evolution, «нет такого треда»,
вид, который мессенджер не умеет, — сразу `failed`. Задача, оборванная выкатом, ставится заново
(`agent.recover_stalled` смотрит и очередь `channels`).

**Повторы (оставшийся риск).** Если мессенджер принял сообщение, а база упала до коммита,
сообщение остаётся `pending`, уборщик через 5 минут отправит его ещё раз — клиент может
получить дубль. В лог пишется `sent (id …) but not marked sent`.

## Instagram Direct

### Вход (`sim/channels/instagram/login.py`, процесс `api`)

Три способа (форма «Подключить → Instagram»):

1. **Логин и пароль.** `client.login` в отдельном потоке. Ответы Instagram:
   - вошли → готово;
   - `TwoFactorRequired` с TOTP / SMS → состояние `code` (`detail` = `totp` | `sms`), код
     уходит повторным `login(..., verification_code=код)` **тем же клиентом** (то же
     устройство); неверный код — «Код не подошёл», до 5 попыток;
   - `TwoFactorRequired` без кода — подтверждение входа на другом устройстве (`device`):
     «Подтвердите вход в приложении Instagram», и SIM сам повторяет вход тем же клиентом через
     8, 15, 25, 40, 60 с (дашборд опрашивает; кнопка «Я подтвердил» — сразу);
   - challenge с кодом по почте / SMS (`challenge`, `detail` = `email` | `sms`): instagrapi
     спрашивает код **изнутри** `login` (`challenge_code_handler`), поэтому вход идёт в
     потоке, а обработчик ждёт код из дашборда (`CodeBridge`, до 9 минут). Неверный код —
     следующий ответ запускает вход заново, Instagram шлёт новый код;
   - «Manual verification required», формы восстановления, капча (`manual`) — подтвердить в
     приложении Instagram и нажать «Повторить».
2. **`sessionid`** — cookie из браузера, где вход уже выполнен (`login_by_sessionid`). Для
   многих аккаунтов с 2FA это единственный путь: приватное API упирается в экраны Bloks,
   которые instagrapi не проходит.
3. **JSON сессии instagrapi** (`dump_settings`, с `authorization_data`): устройство и cookies
   восстанавливаются, проверка — `account_info`.

**Прокси необязателен.** Владелец (2026-11-28): «сделай прокси опциональный, и попробуем без
прокси» — сервер в Германии, она живёт в Германии. Без прокси (и без `SIM_IG_DEFAULT_PROXY`) вход
и вся работа идут с IP сервера (дата-центр Hetzner: Instagram относится к таким адресам строже,
чем к домашним и мобильным, — риск checkpoint выше; логин-лог пишет «no proxy»). С прокси вход и
вся дальнейшая работа идут через
ОДИН прокси со страной, совпадающей с устройством: вход через индонезийский прокси, а опрос с
немецкого сервера — Instagram видит украденную сессию и ставит checkpoint (урок stepan2).
Прокси — состояние клиента, в дамп настроек не попадает, поэтому применяется при каждой сборке
клиента (`build_ig_client`). Страна и язык устройства — из языка персонажа, часовой пояс — её,
и только когда есть прокси.

Канал хранит `{settings (дамп instagrapi), proxy, username, lang, tz_offset_s}`; пароль — только
в памяти незавершённого входа (10 минут). Свой id — `authorization_data.ds_user_id`.

### Приём (`poller.py`)

- `channels:instagram_tick` раз в минуту: подключённые Instagram-каналы активных персонажей, у
  которых подошло время (`SIM_IG_POLL_INTERVAL_S`, 120 с, + до 20 % случайно), получают
  `channels:poll_instagram` (одна ожидающая на аккаунт, один аккаунт не опрашивается дважды
  сразу).
- Опрос читает **сырой JSON** `direct_v2/inbox/` (чаты) и `direct_v2/pending_inbox/` (запросы
  на переписку): 20 новых тредов, по 10 сообщений. Экстрактор instagrapi не используется — он
  падает на пересланных постах и рилсах (`instagram://` в ссылке) и роняет весь опрос.
- Разбор (`parse.py`): текст; пересланный пост / рилс / сторис / профиль — строка с подписью и
  ссылкой (`🎬 смешное видео` + ссылка на рилс); фото, исчезающее фото, GIF, голосовое — вложение
  (скачивается с CDN, до 20 МБ); системные события — пропуск. От старых к новым.
- Стороны — по `user_id` сообщения против своего id. **Без своего id опрос не идёт вообще**,
  сообщение без `user_id` пропускается (fail closed: в stepan2 пустой id записал 1401 своё
  сообщение как сообщения клиента). Свои сообщения не принимаются — SIM записывает отправленное
  сам.
- Повторы: курсор увиденных id в памяти воркера (id, а не время: принятый позже запрос на
  переписку приносит сообщения старше последнего), а `Inbox` принимает сообщение один раз. На
  первом опросе после старта сообщения старше суток пропускаются — это история, не новости.
- Опрос идёт под замком аккаунта: опрос и отправка не делят клиент одновременно. Обновлённые
  cookies сохраняются обратно в канал.

### Отправка (`messenger.py`)

- Текст: `direct_send(text, thread_ids=[тред])`; фото: `direct_send_photo` (файл во временной
  папке), подпись — отдельным сообщением после фото. Голосовых, кружков, видео, файлов в
  приватном API нет — постоянная ошибка (план их и не предлагает).
- «Прочитано»: `direct_send_seen(тред)` — когда её ход действительно начинается
  ([telegram.md](telegram.md), «Прочитано и статусы»), до ответа проходят обычные секунды хода.
- «Печатает» в приватном API нет.
- Лимиты на аккаунт: `SIM_IG_HOURLY_CAP` 150 в час и `SIM_IG_DAILY_CAP` 800 в сутки; сверх — ждать
  свободного места (`RetryAfter`). Счётчики в памяти воркера — перезапуск их обнуляет.

### Ошибки и антибан

| Что ответил Instagram | Что делает SIM |
|---|---|
| challenge / checkpoint / `LoginRequired` | канал `challenge` «нужен повторный вход», задачи ждут 15 мин; опрос не идёт, пока владелец не войдёт заново. Сам SIM **никогда не логинится повторно**: вход с серверного IP — короткий путь к бану |
| `feedback_required`, «please wait», 429, throttled | мягкая блокировка: повтор через 15 мин |
| сеть, прокси, таймаут | обычный повтор |
| нет треда / пользователя, плохой запрос | `failed` сразу |

Известные проблемы: checkpoint при несовпадении страны прокси и устройства; аккаунты с 2FA,
у которых вход по паролю упирается в Bloks — входить по `sessionid`; новые аккаунты
Instagram ограничивает сильнее (меньше писать первым и держаться лимитов).

**instagrapi 3.2 (вход как у текущего приложения).** 2.16 больше не входит (прод, 2026-11-28):
Instagram отвечает 404 на её `qe/sync` (ключ для шифрования пароля — «Не удалось войти
(TypeError)») и `needs_upgrade` на старый `accounts/login` («Your version of Instagram is out of
date» — «UnknownError»). 3.2 входит через Bloks «CAA», как Android-приложение, и берёт ключ из
`launcher/sync`. Двухфакторный код этого входа не говорит, приложение это или SMS: состояние
`code` с `detail = code` («Код двухфакторной проверки»), код уходит тем же клиентом. Неизвестная
ошибка показывает, что сказал Instagram (`message`, до 160 символов), в лог — её `error_type`.

## WhatsApp

### Сервис Evolution API

`evoapicloud/evolution-api:v2.3.7` в `infra/docker-compose.yml` под профилем compose
`whatsapp` — обычный выкат его **не запускает**. Своя база `evolution` в том же Postgres
(создаёт `evolution-init`), Redis не нужен, порт наружу не публикуется: SIM ходит на
`http://evolution:8080` с заголовком `apikey`, Evolution шлёт события на
`http://api:8000/api/hooks/evolution/{channel_id}`. Как включить — [deploy.md](deploy.md),
«WhatsApp». Пока `SIM_EVOLUTION_URL` / `SIM_EVOLUTION_API_KEY` не заданы, меню «Подключить»
показывает WhatsApp недоступным: «Сервис WhatsApp не запущен на сервере».

### Вход (`login.py`)

1. «Показать QR-код»: `POST /instance/create` — инстанс `sim-<id канала>`, `WHATSAPP-BAILEYS`,
   `qrcode`, без групп (`groupsIgnore`), без истории, `alwaysOnline: false` (не отнимать у
   телефона уведомления), `readMessages: false` (прочитано ставит SIM, когда она читает) и
   вебхук: `MESSAGES_UPSERT`, `CONNECTION_UPDATE`, `base64: true` (медиа приходит в событии),
   заголовок `x-sim-webhook-secret` с новым секретом канала. Инстанс уже есть (403 / 409) —
   вебхук ставится заново (`/webhook/set`). Канал сразу хранит `{instance, webhook_secret}` и
   становится `pending`.
2. Дашборд раз в 2 с: `GET /instance/connectionState` — `open` → `connected`, телефон из
   `fetchInstances` (`ownerJid`) в `account_label`; иначе свежий QR (`/instance/connect`).
3. «Отменить подключение»: `DELETE /instance/logout` + `/instance/delete`, канал снова `new`.

### Приём (`receiver.py`, процесс `api`)

`POST /api/hooks/evolution/{channel_id}` без входа в дашборд, но с секретом канала
(сравнение за постоянное время; [api.md](api.md), «Вебхуки»):

- `messages.upsert` → каждая запись → `Inbox.ingest`. Текст из `conversation`,
  `extendedTextMessage` (ответы, ссылки; на что ответил — `stanzaId`), подписей и ответов на
  кнопки; конверты исчезающих и одноразовых сообщений снимаются. Фото / видео / голосовое (PTT)
  / аудио / файл / стикер — вложение с байтами из события. Свои, групповые, статусы и рассылки —
  пропуск.
- Адрес: `@lid` — приватный id WhatsApp без телефона; телефон приходит в `remoteJidAlt`.
  Клиент и чат адресуются jid телефона, если он известен, иначе `@lid`.
- `connection.update`: `open` → `connected` и задача `channels:whatsapp_catch_up`; `close` с
  причиной 401 (устройство отвязали на телефоне) → `challenge` «WhatsApp отвязан на телефоне:
  подключите заново»; другой `close` → `error`.
- Догонялка (`channels:whatsapp_catch_up`, воркер): `POST /chat/findMessages` — последние 50
  входящих, из них за сутки — в `Inbox` (он пропустит уже принятые). Байтов медиа здесь нет —
  вложение без данных.

### Отправка (`messenger.py`)

Текст — `sendText`, голосовое — `sendWhatsAppAudio` (настоящее PTT, `encoding: true`), фото /
видео / файл — `sendMedia`; кружков в WhatsApp нет. «Печатает…» / «записывает аудио…» —
`sendPresence` (`composing` / `recording`, `paused` — снять), повторяется каждые 4.5 с, как в
Telegram. «Прочитано» — `markMessageAsRead` (синие галочки).

### Известные проблемы

- Телефон с номером должен выходить в сеть хотя бы раз в 14 дней, иначе WhatsApp отвязывает
  связанное устройство (придёт `close` 401 → «нужен повторный вход»).
- Не больше 4 связанных устройств на номер.
- Имя устройства в «Связанные устройства» — `EVOLUTION_DEVICE_NAME` (по умолчанию `SIM`):
  незнакомое устройство в этом списке выглядит как угон, и его отвязывают.
- `@lid`-чаты без `remoteJidAlt` не дают телефон клиента.
