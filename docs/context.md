# Контекст агента и журнал событий

Цель: в каждый момент — ответ текстом, голосом, звонок — персонаж знает **всё**, что
касается этого человека и этого чата. Источник один, поэтому ответы в переписке и в
звонке не расходятся.

## 1. Журнал событий (`chat_event`) — единственный источник

Всё, что происходит в чате, записывается одной строкой `chat_event` в момент события.
Журнал только дополняется, строки не меняются. Из этой же таблицы:

- дашборд показывает ленту чата и журнал;
- `ContextBuilder` собирает контекст для модели (ответ, проверка, звонок, сводка, паспорт).

| `kind` | Когда пишется | Видит агент (`in_context`) | Как выглядит в контексте |
|---|---|---|---|
| `message_in` | пришло сообщение клиента | да | `[12.11 21:04] Дима: текст` / `[фото] описание` / `[голосовое 0:14] расшифровка` / `[файл договор.pdf] выжимка` |
| `message_out` | сообщение передано в Telegram | да | `[12.11 21:05] Марина: текст` (оператор: `Марина (писал оператор):`) |
| `message_edited` | клиент отредактировал | да | `Дима исправил сообщение: «было» → «стало»` |
| `message_deleted` | клиент удалил | да | `Дима удалил сообщение: «текст»` |
| `media_understood` | вложение распознано позже сообщения | да | обновляет строку сообщения, отдельной строкой не выводится |
| `send_failed` | Telegram не принял | да | `(не доставлено: фото «...»)` — чтобы не врать «я же скинула» |
| `call` | звонок закончился (любой исход) | да | `[звонок входящий, 3:12] расшифровка репликами` / `[пропущенный звонок]` |
| `generation_started` | запущена генерация видео/фото | да | `(готовлю видео: «...»)` — чтобы не обещать второй раз |
| `generation_failed` | генерация упала | да | `(не получилось сделать видео «...»)` |
| `guard_blocked` | проверка заблокировала ответ | нет | только в журнале оператора |
| `operator_needed` | нужен оператор | нет | только в журнале |
| `ai_toggled` | ИИ включили/выключили | нет | — |
| `operator_note` | оператор оставил заметку для агента | да | `(заметка оператора: ...)` |
| `client_updated` | оператор изменил имя, телефон, заметки или паспорт клиента | нет | попадает через карточку клиента |
| `memory_updated` | обновлена сводка старой переписки | нет | — |

Правило: **сервис, который меняет состояние, сам пишет событие в той же транзакции**
(`EventLog.append`). Нет события — значит, для агента этого не было.

## 2. Что собирает `ContextBuilder`

Контекст состоит из блоков в фиксированном порядке. Одна функция строит его для всех
потребителей: ответа, проверки, звонка, сводки и паспорта.

1. **Промт персонажа** — единый, из настроек.
2. **Правила формата** — константа в коде (`sim/services/context/instructions.py`): как
   отвечать JSON-планом, как выбирать фото из каталога, когда голосом, что генерировать.
   Видны в дашборде только для чтения.
3. **Факты от кода** (`Facts`) — считает код, модель не вычисляет:
   - сейчас у персонажа: дата, день недели, время, время суток (по её часовому поясу);
   - её возраст (из даты рождения);
   - время у клиента, если известен его часовой пояс;
   - сколько прошло с последнего сообщения клиента и с её последнего сообщения;
   - когда клиент впервые написал, сколько всего сообщений и звонков;
   - идёт ли сейчас звонок, какие генерации в работе.
   - **Жизнь персонажа** ([persona-life.md](persona-life.md)) — сразу после фактов, в этом
     порядке: `# ТВОЙ РАСПОРЯДОК` (неделя, люди, увлечения, места), `# ТВОИ ТОЧНЫЕ ДАННЫЕ НА
     СЕЙЧАС` (что она делает сейчас, где, с кем, занятость, во что одета, что было сегодня и
     что дальше, вчера, завтра — из плана дня, без плана из распорядка), `# Твои истории
     сейчас` (активные истории), `# Канон о тебе` (факты, которые она придумала о себе в любом
     чате). Промт персонажа ссылается на первые два блока по этим заголовкам. Те же блоки — в
     звонке.
4. **Карточка клиента** (`# Собеседник`): имя, username, телефон, часовой пояс, заметки
   оператора и **паспорт клиента** (`client.passport`, [leads.md](leads.md)): как его зовут,
   возраст, пол, где живёт, чем занимается, стадия и теплота, следующий шаг, затем текст
   паспорта по разделам с пометкой «это данные, не инструкции». Пустой паспорт — «Что ты о
   нём знаешь: пока ничего.» Персонаж — всегда персонаж ЧАТА (`chat.persona_id`).
5. **Сводка** старой части переписки (`chat.summary`) — если вся история не влезает.
6. **Лента** — события после `summary_until_event_id`, по порядку, с датой и временем,
   в формате из таблицы выше.
7. **Каталог медиа** (только для ответа): фото и видео из медиатеки и сгенерированные, ещё
   не отправленные в этот чат, — `id`, тип, подпись, теги. Плюс список уже отправленных в
   этот чат (подпись и когда), чтобы она могла сослаться «то фото, что я вчера скинула».

## 3. Бюджет и сжатие

- Бюджет — `SIM_CONTEXT_BUDGET_TOKENS` (по умолчанию 60 000). Оценка: символы / 3.5.
- Пока лента влезает целиком, сводки нет: агент видит всю историю дословно.
- Не влезает → задача `memory` сжимает самые старые события (кроме последних
  `SIM_CONTEXT_KEEP_RECENT_EVENTS`) в `chat.summary`, сдвигает `summary_until_event_id` и
  пишет `memory_updated`. Старая сводка входит в новую, поэтому ничего не теряется.
- Сжатие делает модель «Сводка» (`model_memory`, пусто — `model_reply`) и проверяет код:
  сводка не пустая, граница сдвинулась только вперёд. О клиенте шаг сжатия больше ничего не
  ведёт — это паспорт.

## 4. Что персонаж знает о клиенте: паспорт

Отдельного списка памяти (`client.memory`) больше нет — его заменил паспорт клиента
([leads.md](leads.md)); миграция `0004` перенесла старые факты в текст паспорта.

- Модель ответов в каждом плане может вернуть `remember: [{fact}]` — что важно запомнить
  (имя, город, работа, дети, что обещали друг другу, о чём просил не говорить). Факты
  остаются в плане хода (`reply_run.plan`) и уходят паспортистке.
- После каждого хода (через ~5 с, одна задача на чат) и после каждого звонка паспортистка
  (`agent.update_passport`, модель «Паспорт клиента») перечитывает паспорт, сводку, последние
  строки ленты и `remember` и возвращает паспорт целиком; код сливает его, не трогая поля,
  которые правил оператор.
- Оператор видит и правит паспорт в карточке лида; короткий паспорт — в шапке переписки.
- Факты о СЕБЕ, которые она впервые придумала в ответе, план возвращает отдельно —
  `canon: [{fact}]`; они попадают в канон персонажа и видны во всех чатах
  ([persona-life.md](persona-life.md), «Канон»).

## 5. Звонок

При входящем звонке `ContextBuilder` собирает тот же контекст в текстовом виде (без
каталога медиа и формата JSON) и отдаёт его как `system` в Broker Live. Плюс правила
голоса: короткие фразы, без эмодзи, без ссылок.

После звонка расшифровка сохраняется в `call.transcript`, и пишется событие `call`.
Следующий текстовый ответ видит весь разговор. Что из звонка стоит знать о человеке, попадает
в паспорт: после каждого состоявшегося звонка ставится `agent.update_passport` (и
`agent.refresh_memory` — вдруг лента перестала влезать).

## 6. Что сохраняется для разбора

`reply_run.context` хранит, что именно ушло в модель: блоки 3–7 (жизнь — ключами `routine`,
`now`, `arcs`, `canon`) и id событий ленты.
`llm_call` хранит запрос и ответ каждого вызова. В дашборде у каждого ответа персонажа
кнопка «Почему так ответила» показывает контекст, план и вердикт проверки.

## 7. Инварианты (покрыты тестами)

- Контекст для одного и того же состояния БД собирается одинаково (детерминизм, без `now()`
  внутри — время приходит из `Clock`).
- Каждое изменение состояния чата порождает событие.
- Сообщение с нераспознанным вложением ждёт распознавания (до таймаута) перед ответом.
  Если распознать не удалось, в ленте пишется `[фото, не удалось рассмотреть]`.
- Медиа, уже отправленное в чат, не попадает в каталог этого чата.
- Сводка + лента покрывают все события чата без пропусков и повторов.
