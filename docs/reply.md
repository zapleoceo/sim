# Мозг агента: от входящего сообщения до ответа

Код: `backend/sim/services/**`, `backend/sim/tasks/**`. Контекст и журнал событий описаны в
`docs/context.md`, схема БД — в `docs/database.md`.

## 1. Сборка зависимостей

`sim/services/deps.py` — `Deps`: настройки, фабрика сессий, часы и все порты (Broker, хранилище,
ffmpeg-инструменты) плюс очередь задач `TaskQueue`. Точка входа процесса собирает `Deps` один раз
и регистрирует через `set_deps()`; задачи Procrastinate берут их через `get_deps()`.

Сервисы знают только порты (`sim/ports.py`), поэтому в тестах всё подменяется фейками
(`tests/fakes/ai.py`).

## 2. Очередь задач

`sim/services/queue.py` — интерфейс `TaskQueue`, `sim/tasks/queue.py` — реализация на
Procrastinate (`ProcrastinateQueue`). Задачи ставятся по имени, поэтому любой процесс может
поставить задачу, которую выполняет другой.

| Задача | Очередь | Блокировка | Что делает |
|---|---|---|---|
| `agent.reply_chat(chat_id)` | `agent` | `lock=chat:<id>`, `queueing_lock=reply:<id>` | один ход персонажа |
| `agent.understand_media(media_id)` | `agent` | `queueing_lock=understand:<id>` | распознать вложение |
| `agent.run_generation(generation_id)` | `agent` | `queueing_lock=generation:<id>` | сделать фото/видео и отправить |
| `agent.refresh_memory(chat_id)` | `agent` | `lock=chat:<id>`, `queueing_lock=memory:<id>` | сводка и память |
| `telegram.send_message(message_id)` | `telegram` | `lock=send:<chat_id>` | отправка (процесс `telegram`) |
| `telegram:mark_read(message_id)` | `telegram` | `queueing_lock=mark-read:<id>` | «прочитано» до сообщения клиента |
| `telegram:chat_action(chat_id, action, seconds)` | `telegram` | `lock=chat-action:<chat_id>` | живой статус: «печатает», «записывает кружок»… (`docs/telegram.md`) |

- `lock` по чату — один чат обрабатывается строго по очереди (ответ и память не идут параллельно).
- `queueing_lock` у ответа — пока ответ ждёт старта, новый запрос не ставится второй раз
  (`AlreadyEnqueued` молча поглощается). Ожидающий ответ при старте сам смотрит на чат заново:
  если клиент ещё пишет, он переставляет себя (см. п. 4), — так новый запрос фактически
  «заменяет» старый.
- `lock=send:<chat_id>` держит порядок исходящих сообщений одного чата.
- `sim/tasks/app.py` — `make_app(settings)`: приложение Procrastinate с `PsycopgConnector` на той
  же базе (`postgresql+psycopg://` → `postgresql://`). Задачи `agent.*` регистрируются под
  точными именами (`register_agent_tasks`), без префикса blueprint.
- Повторы: при сетевой ошибке Broker (`PortError`) задача повторяется до 3 раз через 20 с;
  остальные ошибки сервис записывает сам (`reply_run.error`, `generation.error`, …).

## 3. Входящие (`sim/services/inbox.py`)

`Inbox.ingest(InboundMessage)`:

1. `resolve_chat` — по `(channel.kind, peer.external_id)` находит `client_identity`; при первом
   контакте создаёт `client` (**ИИ выключен**), `client_identity` и `chat` (ИИ чата включён).
   Известные данные клиента не перезаписываются, только пустые поля заполняются.
2. Идемпотентность: сообщение с тем же `(chat, direction=in, external_id)` второй раз не
   сохраняется (`ingest` вернёт `None`; гонку ловит уникальный индекс).
3. Вложение → медиатека (`source=incoming`, `persona_id=NULL`), `understanding=pending`, если его
   может прочитать модель (изображение, видео, аудио, PDF, текст, офисные документы), иначе
   `skipped` (например, анимированный стикер TGS).
4. `message` (`direction=in`, `status=received`) + событие `message_in`; `unread_count + 1`,
   `chat.last_message_at`, `client.last_seen_at`.
5. После коммита: `understand(media_id)` для вложения и `reply(chat_id, persona.reply_delay_s)`,
   если ИИ включён у персонажа, клиента и чата.

`edited` пишет `message_edited` (было → стало) и обновляет текст. `deleted` пишет
`message_deleted` по каждому найденному сообщению канала (Telegram не сообщает чат); повторное
удаление того же сообщения второго события не даёт.

## 4. Когда отвечать (`sim/services/turn_state.py`, начало `ReplyService.run`)

Сообщение клиента **отвечено**, если после него было исходящее сообщение (`message_out`) или
ход персонажа со статусом `sent`/`blocked` взял его в работу (`reply_run.trigger_event_id`).

Ход не начинается (run не создаётся), если:

- ИИ выключен у персонажа, клиента или чата;
- чат ждёт оператора (`needs_operator`);
- неотвеченных сообщений нет.

Ход откладывается (задача переставляет себя), если:

- последнее сообщение пришло меньше `persona.reply_delay_s` назад — клиент ещё пишет;
- у неотвеченного сообщения вложение ещё распознаётся и с его прихода прошло меньше 90 с —
  проверка повторяется каждые 5 с. После 90 с ход идёт без описания: в ленте
  `[фото, ещё не успела посмотреть]`, а при ошибке распознавания — `[фото, не удалось рассмотреть]`.

## 5. Ход персонажа (`sim/services/reply.py`)

1. **Старт** (транзакция, строка `chat` под `SELECT … FOR UPDATE`): проверки из п. 4, создаётся
   `reply_run` (`running`), собирается контекст (`ContextBuilder.for_reply`), его снимок пишется
   в `reply_run.context`. Если модель ответов не выбрана — run сразу `failed`.
   Сразу после старта персонаж «читает» чат: `mark_read(последнее входящее)` (две галочки) и
   статус «печатает» на 40 с, пока модель думает. Если ход не начался (ИИ выключен, ждём
   оператора, клиент ещё пишет) — ни «прочитано», ни статуса.
2. **План** (без транзакции): модель `persona.model_reply`, `json_schema` = схема
   `ReplyPlan` (`sim/domain/plan.py`). Проверка (`sim/services/plan_check.py`):
   - JSON по схеме (лишние поля запрещены);
   - у фото/видео/кружка ровно одно из `media_id` / `generate`; у нового кружка обязателен
     `generate.speech` (точные слова в камеру);
   - `media_id` только из каталога этого чата («Можно отправить»), нужного типа, без повторов
     в одном ответе;
   - выключенное нельзя: голосовые без голоса/TTS, фото/видео при выключенном переключателе
     (кружки разрешает тот же переключатель видео, `persona.video_enabled`), генерация без
     модели; не больше одной генерации за ход.
   При ошибке — **одна** попытка исправления: модели возвращается её ответ и список ошибок.
   Вторая ошибка — run `failed`.
3. **Проверка** (`sim/services/guard.py`): модель `persona.model_guard` (если не выбрана —
   `model_reply`) получает факты, запреты (`persona.guard_rules`), последние реплики клиента и
   то, что уйдёт клиенту, и отвечает `{"ok", "reason"}`. Проверяется только критичное: не
   признаётся, что ИИ; дата/время/возраст не спорят с фактами; нет запрещённого; не пусто и на
   языке собеседника; не объявляет, что фото/видео/кружок «сейчас запишется» или «придёт
   позже» (живой человек так не пишет — сигнал только статус в Telegram). Неразборчивый ответ проверки = блок (fail closed). Пустой план
   (промолчать) проверку не проходит — проверять нечего.
   - `block` → модель ответов пишет новый план с причиной блокировки;
   - второй `block` → run `blocked`, `chat.needs_operator = true`, события `guard_blocked` (×2)
     и `operator_needed`; клиенту ничего не уходит.
4. **Подготовка** (без транзакции): медленная часть действий — синтез голоса, нарезка
   готового видео в кружок (п. 6). Перед медленной работой действие показывает свой статус
   (`ActionHandler.busy`): голосовое — «записывает голосовое» (30 с), новое фото — «отправляет
   фото» (120 с), новое видео — «отправляет видео», новый кружок — «записывает кружок» (400 с,
   ограничено 300 с). Текст и готовое медиа отдельного статуса не получают.
5. **Фиксация** (транзакция, `chat` под `FOR UPDATE`):
   - если за это время пришло новое сообщение клиента — план выбрасывается (run `skipped`) и
     ответ ставится заново, чтобы не отвечать на устаревшее;
   - если ИИ выключили или чат ждёт оператора — run `skipped`;
   - иначе действия плана пишутся по порядку (исходящие `pending`, генерации `queued`), факты
     `remember` добавляются в `client.memory` без дублей (сравнение по нормализованному тексту:
     регистр, «ё», пробелы, знаки по краям) со ссылкой на событие-триггер, блокировки проверки
     (если были) попадают в журнал, run `sent`.
   - После коммита: `send` для каждого сообщения по порядку, `generate` для генераций,
     `refresh_memory`, если лента не влезла в бюджет.
   - Ход, который ничего не поставил (промолчать, блок, ошибка, план выброшен), снимает статус
     (`cancel`); иначе статус снимет доставленное сообщение. Статусы и «прочитано» ставятся
     без гарантий (`sim/services/presence.py`): сбой только в логе, ход не падает.

Каждый вызов Broker (ответ, проверка, распознавание, TTS, генерация, память) пишется в
`llm_call` одной функцией `logged_call` (`sim/services/llm_log.py`): запрос (байты заменены на
mime и размер), ответ, токены, стоимость, задержка, ошибка. Запись идёт в своей короткой
транзакции, поэтому сохраняется и при упавшем ходе.

## 6. Выполнение плана (`sim/services/actions/`)

Одно действие — один обработчик (`ActionHandler`): `prepare` (вне транзакции, медленное) и
`apply` (в транзакции хода, только строки БД). Реестр `registry.py`; новое действие = новый
обработчик, остальные не меняются.

| Действие | Обработчик | Что происходит |
|---|---|---|
| `text` | `TextHandler` | исходящее текстовое сообщение |
| `voice` | `VoiceHandler` | `speech.synthesize(voice_id, tts_style(voice_style, action.style), model_tts)` (настроение этого голосового + обычная манера, коротко: длинное описание стиля TTS читает вслух или тянет паузами) → WAV → `tools.wav_to_ogg_opus` → медиатека (`generated`, `audio`, в `description` — произнесённый текст) → сообщение `voice`. Если TTS упал — те же слова уходят текстом, пометка в `reply_run.error` |
| `photo` с `media_id` | `PhotoHandler` | сообщение `photo` с этим медиа и подписью |
| `video` с `media_id` | `VideoHandler` | сообщение `video` |
| `video_note` с `media_id` | `VideoNoteHandler` | в `prepare` видео из каталога режется в кружок (`tools.to_video_note`: центр-квадрат 640×640, H.264 yuv420p + AAC, ≤ 60 с, faststart) → копия в медиатеку (`generated`, `video`, подпись и теги оригинала + «кружок») → сообщение `video_note`. Не удалось нарезать — оригинал уходит обычным видео, пометка в `reply_run.error` |
| `photo`/`video`/`video_note` с `generate` | те же | внешняя подпись (если модель её всё же дала) сразу уходит текстом — правила формата просят её не писать; создаётся `generation` (референсы — фото медиатеки с `is_reference`, до 8; для видео и кружка — `speech`), событие `generation_started`, задача `generate`. Объявлений «сейчас запишу» нет: клиент видит только статус |

### Кружок («кружок», «кружочек», «видеосообщение»)

Когда клиент просит кружок, модель отвечает `{"type": "video_note", ...}`. Новый кружок —
это живое видеосообщение именно этому человеку: `generate.speech` — 1–2 коротких предложения
(до 10 с речи), реакция на то, что он только что написал, по имени, если оно известно; без
«всем привет» и без слов о записи или генерации. Текст рядом с кружком — только если сообщение
клиента действительно требует словесного ответа. Пока кружок готовится (минуты), клиент видит
«записывает кружок», потом приходит сам кружок.

## 7. Генерация (`sim/services/generation.py`)

`GenerationService.run(generation_id)` (задача `agent.run_generation`), идемпотентно:
`queued → running` под блокировкой строки.

- **Фото**: `image_gen.generate_image(prompt, референсы, model_image)` → медиатека
  (`generated`, подпись и теги из плана, `generation_id`) → сообщение `photo` → `send`.
- **Видео**: сначала фото по референсам (как выше, тоже остаётся в медиатеке), затем
  `video_gen.generate_video(video_prompt(...), first_frame=это фото, model_video, 5 с)` →
  медиатека → сообщение `video` → `send`.
- **Кружок**: как видео, но 8 с и всегда «селфи со словами»; затем `tools.to_video_note` →
  медиатека (`video`, `video_note-<id>.mp4`, длительность) → сообщение `video_note` → `send`.
- **Промт видео** — одна функция `video_prompt(scene, speech, round_note, language)`: для кружка
  и для видео со словами — вертикальное селфи на фронтальную камеру, взгляд в объектив,
  естественный свет, тепло и непринуждённо, лёгкая тряска в руке; сцена из `prompt`; «She says
  in Russian, exactly: «<speech>»», синхрон губ, без субтитров, музыки и текста на экране. Видео
  без слов — только сцена, как раньше. Фото-первый кадр делается по исходному `prompt`.
- **Статус**: на старте и перед видеошагом — «отправляет фото / видео» или «записывает кружок»;
  результат снимает его при доставке.
- **Ошибка**: `generation.failed` с текстом ошибки и событие `generation_failed`, статус
  снимается (`cancel`); клиенту ничего не уходит, оператор видит строку в ленте, агент —
  `(не получилось сделать видео «…»)` / `(не получилось сделать кружок «…»)`.
- Стоимость шагов суммируется в `generation.cost_usd`.

Сгенерированное фото попадает в каталог медиа других чатов и может быть отправлено по
`media_id` вместо новой генерации.

## 8. Распознавание вложений (`sim/services/understanding.py`)

| Вложение | Как |
|---|---|
| фото, стикер | модель `model_vision`: описание по-русски в 1–3 предложениях, текст на картинке дословно |
| видео | `model_vision` с видео inline (`video/mp4`) |
| голосовое, аудио | `transcriber` с `model_transcribe` |
| кружок | расшифровка + `model_vision`: «Видно: … Говорит: …» |
| PDF | `model_vision` с PDF inline; не вышло — текст через `tools.document_text` |
| DOCX, TXT и др. | `tools.document_text`, до 6000 символов |

Результат — `media_asset.description` и `understanding=done`, ошибка —
`understanding=failed` и `understanding_error`. В обоих случаях пишется `media_understood`
(агенту не показывается — строка сообщения просто обновляется). Повторная задача для уже
распознанного файла ничего не делает.

## 9. Память (`sim/services/memory.py`)

`MemoryService.refresh(chat_id)` (задача `agent.refresh_memory`; ставится ходом, когда лента не
влезла в бюджет, и процессом звонков после каждого звонка):

1. Лента после `summary_until_event_id` оценивается тем же бюджетом, что и в ответе (промт,
   правила и каталог вычитаются из `SIM_CONTEXT_BUDGET_TOKENS`, но лента получает не меньше
   2000 токенов).
2. Если не влезает — всё, кроме последних `SIM_CONTEXT_KEEP_RECENT_EVENTS` событий, идёт на
   сжатие. Плюс звонки после последнего `memory_updated`.
3. Модель `model_memory` (или `model_reply`) возвращает `{"summary", "memory"}`: новую сводку
   (старая + сжимаемые события) и полный обновлённый список фактов о клиенте.
4. Код проверяет: при сжатии сводка не пустая, граница двигается только вперёд и не сдвинута
   параллельно; пустой список фактов не стирает существующую память. Факты, которые остались,
   сохраняют свою исходную ссылку на событие.
5. Пишется `memory_updated`.

Пока лента не сжата, ответ берёт самые новые строки, которые влезают, с пометкой
«(начало переписки не поместилось)».

## 10. Контекст и звонки

`ContextBuilder` (`sim/services/context/`) описан в `docs/context.md`:
`facts.py` (факты от кода), `render.py` (строки ленты по видам событий), `budget.py` (бюджет и
граница сводки), `instructions.py` (правила формата и правила голоса), `builder.py`
(`for_reply`, `for_call`). `for_call` отдаёт тот же контекст текстом + правила голоса,
приветствие «Алло?», голос, модель live и лимит длительности.

## 11. Голоса

`sim/services/voices.py` — 30 готовых голосов Gemini TTS (`GEMINI_VOICES`), которые принимает
Broker; `persona.voice_id` выбирается из них (`GET /api/voices`).
