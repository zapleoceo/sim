## Исправление в кандидате PR #9 и оставшееся ограничение

### Метрика `replied`: только отправленные, не заблокированные исходящие

На базе main до PR #9 `AnalyticsService.message_rows` выбирал сообщения без фильтра
delivery/guard, а `has_exchange` считал любой OUT перед IN обменом. Исправление истории
ИИ в PR #3 этого не меняло. Кандидат PR #9 оставляет все входящие и только `sent`, не
`guard_verdict=blocked` исходящие. `queued`, `failed`, `cancelled` и blocked не увеличивают
`replied`; повторные входящие не увеличивают число клиентов. Persona-фильтр сохраняется.
Счётчики `guard` продолжают считать сохранённые вердикты, включая неотправленные сообщения.
Исправление подготовлено и проверено локально; слияние PR #9 и выкладка не подтверждены.

У `Message` нет `sent_at`: порядок и границы периода остаются приближением по `created_at`,
а не фактическому времени доставки. Более точная семантика требует отдельного изменения
модели и контракта, кандидат PR #9 этого не обещает.

[Кандидат PR #9](https://github.com/zapleoceo/sim/pull/9),
[модель сообщения на базе main](https://github.com/zapleoceo/sim/blob/a7736bcb3d493f25be340f064b92f46e9c2bb14b/backend/sim/adapters/db/models.py).

## Остальные открытые ограничения

### Lease и завершение job без fencing

Rolling pool устраняет ожидание пачки, но истёкший lease долгого обработчика позволяет
другому worker взять ту же job. Complete/fail не проверяют уникальный токен владения.
Нужны отдельный дизайн владения/продления и PostgreSQL-конкурентные проверки; это шире
локального scheduler fix. Durable intent ограничивает повторный upload Instagram,
но не исправляет все другие внешние отправки.

[Очередь](https://github.com/zapleoceo/sim/blob/a7736bcb3d493f25be340f064b92f46e9c2bb14b/backend/sim/worker/loop.py),
[репозитории](https://github.com/zapleoceo/sim/blob/a7736bcb3d493f25be340f064b92f46e9c2bb14b/backend/sim/adapters/db/repositories/jobs.py).

### Независимость guard не доказана во всех случаях

Пустой ID допускается текущей политикой, aliases не распознаются. Rewrite сравнивается
с исходным генератором, а не автором правки: контролер может проверять собственную правку.
Это не повторное открытие уже закрытого known-same-model fallback; нужны отдельные решения
для более строгой идентификации и независимой проверки.

[Контролер](https://github.com/zapleoceo/sim/blob/a7736bcb3d493f25be340f064b92f46e9c2bb14b/backend/sim/services/guard.py).

### Nginx login routes: локальный кандидат исправления, runtime не проверен

Повторно подтверждено на main `ea6e238956001862e4880f01793af975c5413c6e`: усиленный
limit относился к удалённому `/api/auth/login`. Локальный кандидат заменяет его точными
locations для `POST /api/auth/telegram` и `GET /api/auth/link`. Оба используют прежний
общий per-IP budget `sim_login` (`10r/m`, `burst=5`, `nodelay`). Query string одноразовой
ссылки не меняет exact match. `/api/auth/config`, `/api/auth/me`, `/api/auth/logout`,
остальные API и UI остаются на общем `sim_api` (`600r/m`, `burst=120`).

Upstream, `proxy_params`, `X-Forwarded-Proto https` и timeout 120s совпадают с общей
proxy location. Application limiter не менялся: он отдельно считает неудачные попытки
по паре identity/IP и по IP. Статические offline-тесты сверяют routes, limits и proxy
директивы; это не `nginx -t` и не проверка ответов/ограничений работающего nginx.
Слияние кандидата, установка конфигурации и reload не выполнялись. Осталось проверить
синтаксис с реальным `proxy_params`, burst/recovery, query-string вход и обычные auth/read
запросы в разрешённой изолированной среде. Фактическое состояние live nginx неизвестно.

[База nginx](https://github.com/zapleoceo/sim/blob/ea6e238956001862e4880f01793af975c5413c6e/infra/nginx-sim.conf),
[роуты auth](https://github.com/zapleoceo/sim/blob/ea6e238956001862e4880f01793af975c5413c6e/backend/sim/api/routers/auth.py),
[проверки nginx](operations.md#проверка-nginx-login-routes).

### Origin TLS требует отдельного подтверждения

Комментарий Flexible и `listen 80` остаются в репозиторном nginx-config. Если production
ему соответствует, участок Cloudflare → origin не защищён TLS. Реальная конфигурация,
firewall и сертификаты не проверены. Следующий шаг только в рамках отдельно разрешённого
инфраструктурного доступа, затем согласованное изменение. Не обходить отказ доступа.

[Репозиторная конфигурация](https://github.com/zapleoceo/sim/blob/a7736bcb3d493f25be340f064b92f46e9c2bb14b/infra/nginx-sim.conf).

## Что ещё проверить перед готовностью соответствующих сценариев

- Сбой commit после обычной внешней отправки или timeout с неизвестным исходом: durable
  intent защищает Instagram content upload, но не все исходящие сообщения каналов.
- Пересланный ref-код и ошибочное объединение людей, повтор webhook, параллельное создание
  первого диалога, lease expiration и долгие jobs с ограниченным DB pool.
- Миграции и PostgreSQL advisory locks/SKIP LOCKED; SQLite-тесты их не подтверждают.
- Backup/restore с сохранением publication intent history, измеренные RPO/RTO.
- Изолированная браузерная UX-проверка по брифу: понятность каналов, статусов и ошибок,
  настройка персонажей и минималистичность админки.
- Голоса, аватары и выходящие видео: поля/порты не означают готовую внешнюю интеграцию.

## Проверки и следующий порядок работ

1. Завершить проверку и рассмотрение кандидата PR #9; ограничение `created_at` сохраняется.
2. Проверить nginx-кандидат в изолированном nginx runtime; source fix не означает deployment.
   Отдельно исследовать job fencing и guard metadata.
3. Пройти доступные frontend build/unit/browser и PostgreSQL integration checks.
4. Инфраструктуру, live каналы и Instagram-пилот проверять только при отдельном разрешении.
   Флаги публикации Instagram остаются выключенными по умолчанию; эта работа их не включала.

Последняя локальная проверка кандидата PR #9: **464 backend-теста прошли**, 16 существующих
предупреждений Alembic; **Ruff прошёл**. TypeScript app/spec и ESLint ранее прошли на неизменённом frontend. Spec скомпилированы,
не выполнены. Последняя Angular build **не подтверждена**: сетевой доступ
к npm registry не был разрешён. Browser/Karma **не запускались** из-за
известного ограничения среды на сокеты. PostgreSQL locking, реальные публикации,
production health и фактическая выкладка **не проверены**.
