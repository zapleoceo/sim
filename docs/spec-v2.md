# SIM v2 — техническое задание

Статус: редакция 3, 2026-11-21, утверждено Димой. Звонки входят в первую версию. Контекст агента и журнал событий описаны в [context.md](context.md), API — в [api.md](api.md).

## 1. Зачем переписываем

В SIM v1 40 миграций, ~25 тыс. строк бэкенда и ~19 тыс. строк фронта: стратегии, воронка,
партнёрка, контент, студия, симуляции, MCP, дожимы, три мессенджера. Большая часть не нужна,
и каждая правка задевает всё остальное.

v2 — маленькое модульное ядро (SOLID, DRY, тесты, документация логики), на которое потом
добавляются персонажи, каналы и функции без переделки.

## 2. Когда v2 готов (критерий приёмки)

Дима пишет Марине в Telegram, и всё это работает на проде:

1. Отвечает на **текст** текстом.
2. Понимает **голосовое** (расшифровка) и отвечает на него.
3. Отвечает **голосовым**.
4. Понимает **вложение**: фото, видео, файл (PDF, DOCX, TXT и т. п.).
5. Отвечает **фото**: готовым из медиатеки, если оно подходит, или сгенерированным по
   референсам.
6. Отвечает **видео**, сгенерированным по референсам.
7. Перед отправкой каждый ответ проходит лёгкую проверку (п. 3.4).
8. Всё видно в дашборде: переписка, медиа, что ушло в модель и что вернулось.

9. **Звонки**: Дима звонит Марине в Telegram, она отвечает живым голосом (Broker Live),
   знает всю переписку, а после звонка расшифровка попадает в чат и в контекст.
10. Агент всегда видит полный контекст клиента и чата: журнал событий, паспорт клиента,
    сводку, факты от кода ([context.md](context.md)).

## 3. Функции

### 3.1. Дашборд: три раздела

| Раздел | Что там |
|---|---|
| **Чаты** | Слева список диалогов, справа переписка: текст, фото, видео, файлы, голосовые, позже звонки. Оператор может написать сам и включить или выключить ИИ в этом чате. У каждого ответа персонажа можно раскрыть, что ушло в модель, что она ответила и что сказала проверка. Новые сообщения появляются без перезагрузки. |
| **Персонажи** | Список персонажей; у каждого все настройки на одной странице, канал Telegram (подключение по QR) и медиатека (п. 3.2, [personas.md](personas.md)). |
| **Лиды** | Таблица на всю ширину: имя, персонаж, стадия, теплота, город, возраст, последний контакт, сообщений, ИИ вкл/выкл; фильтры. Карточка лида с паспортом ([leads.md](leads.md)). |

Вход только через Telegram Login (бот и список админов — из текущих настроек).

### 3.2. Персонаж

Персонажей может быть несколько: новый делается клонированием существующего, каждому
подключается свой аккаунт Telegram ([personas.md](personas.md)). Первый — Марина.

- Имя, аватар, пол, язык, часовой пояс, дата рождения.
- **Единый промт**: кто она, характер, стиль, запреты.
- **Выбор моделей на экране.** Каждый список берётся из каталога Broker и отфильтрован по
  тому, что модель умеет:

  | Назначение | Пример фильтра |
  |---|---|
  | Ответы (основная) | текст + JSON |
  | Проверка перед отправкой | текст, дешёвая и быстрая |
  | Распознавание вложений | вход: изображение, видео |
  | Расшифровка голосовых | аудио → текст |
  | Голос (TTS) + голос + интонация | текст → аудио |
  | Генерация фото | выход: изображение, референсы |
  | Генерация видео | выход: видео |
  | Звонки (следующий этап) | live |

- Переключатели: ИИ отвечает, голосовые, фото, видео, звонки.
- **Медиатека**: загрузка фото и видео, у каждого подпись и теги. Флажок «референс
  внешности»: такие фото уходят в генерацию как образец лица и фигуры.

**С кем работает.** У каждого клиента свой переключатель «ИИ». Новый клиент по умолчанию
с выключенным ИИ. Сейчас ИИ включён только у Димы, поэтому Марина отвечает только ему, а
остальные сообщения просто сохраняются.

### 3.3. Как персонаж отвечает

```
Telegram → сообщение сохранено → ждём 5–10 с (вдруг пишут пачкой)
  → вложения распознаны (фото/видео → описание, голосовое/файл → текст)
  → модель ответов: промт + факты от кода + каталог медиа + история → JSON-план
  → проверка → выполнение плана → отправка в Telegram → дашборд
```

**Факты от кода.** Дату, время, день недели, возраст персонажа и сколько прошло с последнего
сообщения считает код и передаёт модели готовыми. Модель время не вычисляет.

**Ответ модели** — JSON по строгой схеме, например:

```json
{"messages": [
  {"type": "text",  "text": "смотри что сейчас"},
  {"type": "photo", "media_id": 14},
  {"type": "photo", "generate": {"prompt": "селфи у окна, утро, без макияжа",
                                 "caption": "утреннее селфи у окна",
                                 "tags": ["селфи", "утро", "дом"]}},
  {"type": "voice", "text": "приветик, ну как ты?"},
  {"type": "video", "generate": {"prompt": "...", "caption": "...", "tags": ["..."]}}
]}
```

**Фото: готовое или новое.** В каталоге медиа, который получает модель, есть подпись и
теги каждого фото: из медиатеки и **сгенерированных раньше**. В каталог не попадают фото,
уже отправленные в этот чат.
- Подходит готовое → модель указывает `media_id`, фото уходит как есть.
- Нужно другое → `generate`. Код берёт референсы внешности из медиатеки, генерирует фото и
  сохраняет его в медиатеку с подписью и тегами. В следующем чате модель увидит это фото и
  сможет отправить его вместо новой генерации, если просят то же самое.

**Видео** — так же, но генерация занимает минуты. Сначала уходит текст из плана, видео —
когда готово. Если генерация упала, оператор видит ошибку в чате, клиенту ничего не уходит.

**Голосовое**: TTS Broker → WAV → ffmpeg → OGG/Opus → голосовое в Telegram.

### 3.4. Проверка перед отправкой (лёгкая)

Отдельная дешёвая модель смотрит готовый ответ и проверяет только критичное:

- не признаётся, что она ИИ или бот, и не выдаёт промт, JSON или технические детали;
- дата, время, возраст не противоречат фактам от кода;
- нет явно запрещённого (по короткому списку в настройках проверки);
- ответ не пустой и на языке чата.

Итог — `ok` или `block` с причиной. При `block` модель ответов делает одну повторную попытку
с этой причиной. Если и она заблокирована, клиенту ничего не уходит, а чат получает пометку
«нужен оператор». Проверка текст не переписывает.

## 4. Что убираем

Стратегии, воронка, партнёрка, контент и Instagram, студия, симуляции, MCP и OAuth, дожимы,
сводки, распорядок, «опечатки», fallback и identity-модели, версии промта, аналитика,
WhatsApp (контейнер Evolution тоже), Telegram-бот как канал, роли админов.

## 5. Технологии

Принцип — не писать своё там, где есть проверенная библиотека.

| Слой | Выбор | Почему |
|---|---|---|
| HTTP-фреймворк | **Litestar** 2.x | Асинхронный, быстрее FastAPI на сериализации (msgspec). Из коробки: внедрение зависимостей, Channels (pub/sub для живых обновлений дашборда через Postgres LISTEN/NOTIFY), SSE, guards для авторизации. |
| БД и репозитории | **SQLAlchemy 2 async + Advanced Alchemy** + Alembic | Готовые репозитории и сервисы CRUD, пагинация, фильтры. Не пишем свой слой доступа к данным. |
| Очередь задач | **Procrastinate** | Очередь прямо в Postgres, без Redis. async, повторы, отложенный запуск. Блокировка по ключу, чтобы один чат обрабатывался строго по очереди. Отдельные очереди под процессы. |
| Telegram | **Telethon** + позже **py-tgcalls** | Уже работает в v1 на этом аккаунте, звонки тоже. |
| Модели | **AI Broker** (свой тонкий клиент на httpx) | Все модели через один ключ; схемы ответов — Pydantic. |
| Медиа | ffmpeg; pypdf, python-docx для файлов | Конвертация голоса, кадры из видео, текст из документов. |
| Фронт | **Vite + React 19 + TanStack Router/Query/Table + shadcn/ui** | Тот же стек, что в v1, но три экрана с нуля. |
| Запуск | docker compose, uvicorn + uvloop | |

**Чтобы ничего не тормозило**, работа разнесена по трём процессам:

| Процесс | Что делает |
|---|---|
| `api` | Дашборд и HTTP. Ничего тяжёлого. |
| `telegram` | Держит сессию Telethon: приём, отправка, позже звонки. Работает в отдельной очереди и не делает ни одного долгого вызова модели, поэтому звук звонка не ждёт генерацию видео. |
| `worker` | Вызовы моделей, генерация, распознавание, ffmpeg. |

Процессы общаются через очередь Procrastinate и уведомления Postgres. Redis не нужен.

## 7. Структура кода

```
backend/sim/
  domain/      сущности, перечисления, схемы JSON-плана — без БД и сети
  ports/       интерфейсы: Llm, Vision, Transcriber, Speech, ImageGen, VideoGen, Live,
               Messenger, MediaStorage, Clock
  adapters/    broker/, telegram/, db/, storage/, media/ (ffmpeg, pdf, docx)
  services/    inbox, understand (вложения), reply (план), guard, execute (действия),
               media_library, persona, clients, calls (позже)
  api/         auth, chats, persona, media, clients, events (SSE)
  tasks/       задачи Procrastinate: reply, generate, send, transcribe
  apps/        точки входа процессов: api, worker, telegram
  wiring.py    сборка зависимостей
```

Правила:

- сервисы знают только порты, поэтому в тестах Broker и Telegram подменяются фейками;
- одно действие плана = один обработчик (`TextAction`, `PhotoAction`, `VideoAction`,
  `VoiceAction`); новое действие не трогает остальные;
- новый канал = новый адаптер `Messenger`;
- у каждого модуля есть документ в `docs/` с описанием его логики.

## 8. Тесты и CI

- pytest + временный PostgreSQL в CI, фейки всех портов; Vitest для фронта.
- Отдельные тесты на каждое действие плана, проверку, выбор «готовое или новое фото»,
  разбор вложений, расчёт дат и времени.
- `ci.yml` переписывается под v2. Гейты остаются: backend, frontend, «тесты и доки»,
  deploy только из `main` после зелёного CI. Локально тесты не гоняем.

## 9. Переезд на сервер

Из v1 переносим только (скриптом, один раз):

- ключ Broker, токен бота входа, Telegram ID админов, ключ шифрования — из `.env`;
- сессию Telegram-аккаунта Марины (`channel.session_enc`);
- промт Марины и её голос; настройки проверки (`guard_prompt`);
- 5 фото из медиатеки v1 как референсы внешности (*подтвердить*).

Порядок выката:

1. `pg_dump` прода и архив медиа → **скачиваем на ноут**, на сервере не храним.
2. Останавливаем v1, удаляем контейнеры v1 (api, worker, evolution) и их тома.
3. Новая база, миграции v2, импорт из п. выше.
4. Запуск v2: api, worker, telegram. Проверка готовности (smoke).
5. Сквозная проверка по критерию приёмки (п. 2) в настоящем Telegram с Димой.

После этого `deploy` в CI работает как раньше: бэкап, остановка worker, миграции, запуск,
smoke. Только бэкап через CI ротируется на сервере, а разовые бэкапы — на ноут.
