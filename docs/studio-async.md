# Очередь Studio

Проверено на `eb7f1728`. Личная привязка Studio связывает действующего
владельца с настроенным Telegram ID. Черновики и выдача файлов уже изолированы.

| Операция | Что происходит на этой базе |
| --- | --- |
| `POST /api/studio/chat` | API ждёт каталог подписок, затем завершение текстовой задачи Broker. |
| `POST /api/studio/media` | Production отвечает 423. Если создать сервис с разрешением, речь ждёт синхронный `/v1/speech`. Видео посылает `/v1/video/jobs`, сохраняет remote ID, затем делает первую сверку в том же HTTP-запросе. |
| `POST /api/studio/media/{id}/reconcile` | Production отвечает 423. Разрешённый тестовый сервис читает только сохранённую квитанцию видео. |
| `GET /api/studio/media/{id}` и `/artifact` | Читают локальный `StudioOperation` и уже сохранённый артефакт. |
| `GET/PUT /api/studio/media/draft/video` | Локальный черновик с ревизией. Запросов к провайдерам нет. |
| `GET /api/studio` | Получает каталог подписок по HTTP для личного аккаунта. Это чтение без генерации. |

Видео уже использует очередь **Broker**. Локальная запись `StudioOperation`
предохраняет от повторной отправки, но сама не создаёт задание worker SIM.

## Приватный кандидат текстового чата

`POST /api/studio/chat-operations/{key}` атомарно сохраняет зашифрованный вход
в `StudioChatOperation` и задание `STUDIO_CHAT` в обычной очереди SIM.
После коммита отвечает 202. `GET` по тому же адресу возвращает статус или
ответ. Повтор того же ключа с тем же телом возвращает исходный ID. На аккаунт
допускается одна ожидающая или неизвестная операция. Истечение аренды
выполнявшейся операции переводит её в неизвестный исход. Повтор провайдера
в такой ситуации запрещён.

Worker повторно проверяет Owner, Telegram-привязку и уже действующую
доступность проверенной подписочной модели перед вызовом. Запрос и результат
хранятся зашифрованными до часа. Очистка выбирает до 200 операций с
оставшимся зашифрованным содержимым в порядке срока и ID. Короткая блокировка
batch пропускает занятые строки. Очищенные строки не задерживают следующие. Общий трассировочный журнал не получает тело
или Broker exchange. `SIM_STUDIO_CHAT_QUEUE_ENABLED` выключен по умолчанию.
Действующий чат и интерфейс остаются на существующем маршруте.

При отдельном переключении UI в `studio-page.tsx` и `api/studio.ts` браузер
должен сохранить ID до POST, опрашивать GET, восстановить тот же ID после
перезагрузки только для текущей привязки и прекратить опрос при смене аккаунта.
После потери ответа POST использовать GET. Старый маршрут нужен для
совместимости, пока новый доступ не подтверждён.

## Переход генерации медиа

1. В `studio_media.py` отделить создание от выполнения. В транзакции под
   существующей блокировкой строки AdminUser сохранить в `StudioOperation`
   владельца, binding, отпечаток, состояние pending, зашифрованный краткоживущий
   вход и отдельное задание worker. Вернуть 202 только после коммита.
2. Worker переведёт состояние в unknown отдельной фиксацией **до** отправки.
   Повтор того же ID возвращает прежнюю квитанцию. Новый ID при неясном исходе
   остаётся запрещённым. При известном remote ID делать только scoped GET.
3. Для видео без локально сохранённого remote ID нужен доказуемый поиск по
   неизменяемому ключу в текущем проекте Broker. Для речи требуется готовый
   асинхронный контракт с теми же гарантиями. До подтверждения обоих контрактов
   очередь не включает генерацию. Бюджет, лимиты и проверка артефакта сохраняются.
4. `media-controls.tsx` после 202 опрашивает существующий GET статуса, а
   готовый файл получает через действующий приватный маршрут. Проверить
   потерю ответа после первой отправки, смену привязки, отсутствие доступа
   у другого владельца и восстановление только чтением после перезагрузки.
