# Telegram: аккаунт персонажа (userbot)

Код: `backend/sim/telegram/`. Тесты: `backend/tests/telegram/`, фейки — `backend/tests/fakes/telegram.py`.
Звонки описаны отдельно в [calls.md](calls.md).

Персонаж говорит через личный аккаунт Telegram (MTProto, Telethon), не через бота. Всё, что
держит сессию Telethon, работает в отдельном процессе `telegram`: приём, отправка, звонки.
Вызовов текстовых моделей в этом процессе нет — они в процессе `worker`.

## Процесс `telegram` (`process.py`)

`run_telegram_process(deps, app=None)`:

1. Закрывает звонки, оставшиеся `ringing`/`active` после прошлой остановки (статус `failed`,
   «interrupted by a restart»), и пишет по ним событие `call`.
2. Создаёт `ChannelRuntime` с двумя «крючками» на каждое новое подключение аккаунта:
   `Receiver` (входящие → `Inbox`) и `CallsAttacher` (py-tgcalls → `CallService`; только если
   `SIM_CALLS_ENABLED=true`).
3. Регистрирует `TelegramMessenger` и `Presence` (живые статусы) для задач очереди
   `telegram` (`tasks.set_runtime`).
4. Запускает воркер Procrastinate на очереди `telegram` (параллельно до 4 задач).
5. Раз в минуту перечитывает каналы: подхватывает новые и заново подключённые аккаунты.
6. По SIGTERM/SIGINT: воркер доделывает текущие задачи, клиенты отключаются.

`app` — уже открытое приложение Procrastinate (то же, через которое `deps.tasks` ставит
задачи); если не передано, процесс создаёт его через `sim.tasks.app.make_app` и открывает сам.

## Подключение аккаунтов (`client.py`)

- `build_client` — **единственное** место, где создаётся `TelegramClient`: `StringSession`,
  прокси (`socks5://user:pass@host:port`, схема по умолчанию socks5), `receive_updates=True`,
  `flood_sleep_threshold=0` (FloodWait не «проглатывается» сном внутри Telethon, а всплывает
  в задачу отправки), `auto_reconnect=True`.
- Учётные данные лежат зашифрованными (Fernet, `SIM_SECRET_KEY`) в `channel.credentials_enc`:
  JSON `{"api_id", "api_hash", "session", "proxy"}`. Никогда не пишутся в лог.
- `ChannelRuntime.start()` берёт все каналы `telegram_user`, кроме `disabled`, и на каждый
  запускает «надзирателя»:
  - подключиться → проверить авторизацию → `get_me()` → канал `connected`, `account_id`,
    `account_label` (`@username` или `+телефон`), `last_error = null` → вызвать крючки;
  - ждать, пока Telethon окончательно не потеряет соединение → `error` «disconnected» →
    пауза → снова;
  - паузы растут: 2, 5, 15, 30, 60, 120, 300 с; после успешной сессии отсчёт с начала;
  - **мёртвая сессия** (не авторизована, отозвана, разлогинена, бан, нет или не читаются
    учётные данные) → `error` с причиной, повторов нет. Надзиратель перезапустится, когда
    вход выполнят заново и канал выйдет из статуса `error` (проверка раз в минуту).
- `runtime.client(channel_id)` отдаёт подключённый клиент или `PortError(retryable=True)`,
  пока аккаунт переподключается — задача отправки просто повторится позже.

## Приём (`receiver.py`)

Обработчики Telethon: `NewMessage(incoming=True)`, `MessageEdited(incoming=True)`,
`MessageDeleted`.

- Берутся **только личные чаты с людьми**: не группы и каналы, не боты, не удалённые
  аккаунты, не служебный аккаунт Telegram (777000), не мы сами.
- Свои исходящие сообщения игнорируются: то, что отправил SIM, записывает задача отправки;
  то, что кто-то написал с телефона мимо SIM, в чат агента не попадает.
- `external_id` сообщения — номер сообщения Telegram. В личных чатах он уникален в пределах
  аккаунта, поэтому удаление (Telegram присылает только номера, без чата) сопоставляется
  напрямую: `Inbox.deleted(channel_id, ["40", "41"])`. Удаления с указанным чатом (каналы,
  супергруппы) не наши и пропускаются.
- `Peer` клиента: `external_id` = id пользователя, `access_hash`, имя (имя + фамилия),
  username, телефон с `+`.
- Вложения (`InboundAttachment`), порядок проверки важен:
  `photo → sticker → voice → video_note → video (и gif) → audio → document (= file)`.
  Видеостикер — это стикер, голосовое — не «аудиофайл». Для каждого: байты, mime (если
  Telegram не дал — по виду), имя файла, длительность, ширина и высота.
- Лимит скачивания **20 МБ**. Больше лимита или скачать не удалось → вложение всё равно
  передаётся, но с пустыми `data`: Inbox знает, что клиент что-то прислал.
- Превью ссылки — не вложение (Telethon иначе отдал бы картинку превью как фото).
- Сообщения одного человека передаются в Inbox **строго в порядке прихода**: Telethon
  обрабатывает каждое обновление в своей задаче, и медленная загрузка фото не должна
  переставить пачку сообщений. Блокировка на человека берётся до первого `await`.
- Ошибка Inbox логируется и не роняет обработчик.
- Правки → `Inbox.edited(channel_id, peer, external_id, новый_текст)`.

## Отправка (`messenger.py`, `tasks.py`)

`TelegramMessenger` реализует `MessengerPort`:

| Вид | Как уходит |
|---|---|
| `text` | `send_message`; длиннее 4096 символов — частями по границе строки/пробела, возвращается id первой части; сбой после первой части логируется, не повторяется (иначе дубль) |
| `photo` | `send_file` с подписью (до 1024 символов) |
| `video` | `send_file`, `supports_streaming` |
| `voice` | OGG/Opus как голосовое (`voice_note`, атрибут длительности) |
| `video_note` | настоящий «кружок»: `video_note=True` и явный `DocumentAttributeVideo(round_message=True, w=640, h=640, duration)`; файл заранее приведён к квадрату 640×640, H.264 + AAC, ≤ 60 с (`tools.to_video_note`) |
| `file` / `sticker` | документ (`force_document`) с подписью |

- Адрес клиента — `InputPeerUser` из сохранённого `access_hash`; без него — кэш Telethon,
  прогретый одним списком диалогов. `access_hash` хранится в `client_identity` по виду канала:
  при втором аккаунте Telegram его надо будет хранить по каналу.
- Отправки одного аккаунта идут по одной и не чаще `SIM_TG_MIN_SEND_INTERVAL_S` (1.5 с).
- Ошибки → `PortError`: FloodWait / slow mode → `FloodWait(seconds)`, повторяемая; коды
  400/401/403/406 (заблокировал, нет такого пользователя, приватность, плохой файл) и
  `ValueError` Telethon → **постоянная**; остальное (500, сеть, таймаут, аккаунт
  переподключается) → повторяемая.
- `set_typing` («печатает», «записывает голосовое», «записывает кружок», «отправляет фото…»)
  — без гарантий: сбой не мешает отправке.
- `mark_read(channel_id, peer, external_id)` — прочитано до этого сообщения (две галочки).

### Задача `telegram:send_message(message_id)`

Очередь `telegram`, выполняет процесс `telegram`.

1. Загрузить `message`; если оно уже не `pending` или не исходящее — пропустить (повтор
   задачи безопасен).
2. Чат → идентичность клиента в Telegram (`Peer`), для медиа — байты из хранилища и
   `mime`, имя файла, длительность из `media_asset`.
3. Показать действие правдоподобное время, от 1 до 6 секунд: текст — длина / 14 символов в
   секунду; голосовое и кружок — их длительность; фото, видео, файл — 1 с. Действие
   повторяется каждые 4.5 с (Telegram показывает его ~5 с).
4. Отправить. Успех → `outbox.mark_sent(session, message, external_id, now)` в одной
   транзакции (событие `message_out`), затем `Presence.sent(chat, kind)` — см. «Прочитано и
   статусы».
5. Ошибка:
   - постоянная → `outbox.mark_failed` (событие `send_failed`), задача завершается;
   - повторяемая → исключение, Procrastinate повторит: после FloodWait — через запрошенные
     секунды + 1, иначе 5, 10, 20, 40, 80 с (максимум 300); всего до 5 повторов;
   - повторяемая на последней попытке → `mark_failed`.
   Сообщение без нужного файла (нет `media_id`) — постоянная ошибка.

Порядок сообщений одного ответа обеспечивает тот, кто ставит задачи: `deps.tasks.send`
должен ставить их с блокировкой Procrastinate по чату (`lock=f"chat-{chat_id}"`).

### Задача `telegram:mark_read(message_id)`

Для входящего сообщения с `external_id`: отметить чат прочитанным до него. Без повторов:
не получилось — запись в логе.

## Прочитано и статусы

Персонаж ведёт себя как живой человек: читает, «печатает», «записывает кружок».

- **Прочитано.** Когда ход персонажа действительно начинается (после паузы на «клиент ещё
  пишет», ИИ включён везде, чат не ждёт оператора), воркер ставит
  `deps.tasks.mark_read(id последнего входящего)` → задача `telegram:mark_read` → клиент видит
  две галочки. Если ИИ выключен или ход не начался — сообщения остаются непрочитанными.
- **Статусы** (`sim/telegram/presence.py`, `Presence`). Telegram показывает действие ~5 с,
  поэтому длинный статус повторяется каждые 4.5 с, пока не истёк срок. На чат один статус
  (действие, до какого времени):
  - новый запрос заменяет действие и срок (и сразу отправляется);
  - `cancel` (или 0 секунд) останавливает повтор и снимает статус в Telegram;
  - доставленное сообщение останавливает статус, если это то, чем персонаж был занят:
    «печатает» — любое сообщение, остальное — только своё (текст, ушедший пока делается
    видео, не снимает «отправляет видео»);
  - срок одного запроса — не больше 300 с; генерация обновляет статус перед долгим шагом;
  - сбой `set_typing` только пишется в лог; при остановке процесса все повторы гасятся.
- Какое действие для чего — одна таблица `sim/domain/presence.py` (`chat_action_for`,
  `busy_with`), её используют ход, исполнитель плана, генерация и задача отправки:

| Чем занят | Действие | Сколько держать |
|---|---|---|
| модель пишет план | `typing` | 40 с |
| синтез голосового | `record_audio` | 30 с |
| новое фото | `upload_photo` | 120 с |
| новое видео | `upload_video` | 400 с → 300 с |
| новый кружок | `record_round` | 400 с → 300 с |
| ход ничего не отправил (молчание, блок, ошибка) / генерация упала | `cancel` | — |

Готовое медиа по `media_id` и текст отдельного статуса не получают: хватает короткого
действия задачи отправки (п. 3 выше).

### Задача `telegram:chat_action(chat_id, action, seconds)`

Очередь `telegram`, `lock=chat-action:<chat_id>` — запросы одного чата применяются по порядку,
без `queueing_lock` (`cancel` не должен поглотиться ожидающим `typing`). Чат →
`(channel_id, Peer)` тем же помощником, что и у отправки (`chat_address`); неизвестное действие
или чат — пропуск с записью в лог. Воркер ставит её через `deps.tasks.chat_action(...)`
(`sim/services/presence.py`: ошибка постановки только логируется и не роняет ход).

## Подключение в приложение

- `sim.tasks.app.make_app`: `app.add_tasks_from(sim.telegram.tasks.blueprint,
  namespace="telegram")`; имена задач — `telegram.tasks.SEND_TASK`, `MARK_READ_TASK`,
  `CHAT_ACTION_TASK`.
- `set_runtime` создаёт и `TelegramMessenger`, и `Presence` (`get_presence()`); процесс
  закрывает `Presence` при остановке.
- Задачи берут зависимости из `sim.tasks.app.get_deps()` (`sessions`, `storage`, `clock`).
